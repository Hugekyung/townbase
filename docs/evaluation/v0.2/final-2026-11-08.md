## 조건과 해석

OPS/SHOP은 각각 별도 빈 합성 설치에서12문서·12chunk로 시작했다. 형식은 PDF/DOCX/MD/TXT 각3개다. 질문/정답표는 색인하지 않았으며 실제 업로드·추출·명시 색인과 C 비용 예약을 사용했다. 초기 설치 후 실패를 포함해 자료/비용 이력을 유지했고, 최종 candidate4는 집합별60문항×3회다. 질문은 독립 새 대화이며 이전 질문 문맥을 주지 않았다.

Linux amd64 Node24.19.0 컨테이너를 ARM 호스트에서 에뮬레이션했다. 각 집합 앱1.5CPU/3GiB, 공용 DB1CPU/2GiB로 평가 할당 합계4CPU/8GiB다. 호스트 VM은10CPU/약8GiB이고 다른 격리 검증도 함께 실행했다. native x86_64 전용 장비 성능/전체200문서·5,000chunk/고객 비공개 자료의 결과로 일반화하지 않는다. 각 manifest의 CPU/cgroup/이미지·파서·migration·문서/질문/컴파일 hash가 실제 조건이다.

최종 답변 품질은 candidate4의 고정 compiled policy/provider/execution으로 측정했다. 이후 채팅 목록/메시지 UI·stop·source promptLabel 표시는 추가했지만 모델/문서/질문/전송 prompt/schema는 바꾸지 않았다. 현재 source/build의 서식 차이와 실제 평가 artifact hash를 혼동하지 않는다. 기록된 latencyMs에는 ask 반환 뒤 평가기의 turn/비용 ledger 재조회 시간도 포함된다. 따라서 표의 전체 응답 시간은 서비스+평가 후처리의 측정 상한이며 순수 서비스 latency가 아니다. 브라우저/인터넷 왕복 시간은 제외한다. 수정한 runner는 ask 반환 직후 측정한다. UI는 별도 합성 공급자로 기능만 검증했다.

새 실행기는 `/data/evidence/<corpus>/<series>`를 사용하고, 최초 실행 manifest의 소스 SHA·compiled hash·문항/문서 hash·반복 범위를 재개 때 대조한다. 재현 예시의 APPROVED_EVALUATION_SOURCE_SHA에는 실제 검증한 소스 commit40자 SHA를 설정한다. performance 결과는 `/data/evidence/<corpus>/performance/<series>`이고 같은 이름은 유료 작업 전에 거절한다. private 평가도 기존 series 디렉터리를 덮지 않는다.

동일 basic series의 동시 실행은 `.run.lock`으로 거절한다. 강제 종료 후 lock이 남으면 진행 중인 평가 프로세스/비용 상태를 먼저 확인한 운영자만 수동 정리한다. 재개 시 원래 manifest가 없거나 Agent/모델 설정이 달라지면 거절한다.
