2026-10-25. 기준 main `bccefe0`(PR #37 병합). 작업 브랜치 `codex/v02-c02-c03-integration-settings`. 첫 PR 범위의 구현·검증 기록이다. 2026-10-25 사용자가 commit/push·main 대상 PR 생성을 승인했다. 첫 전달은 `53b95e7`과 [PR #38](https://github.com/Hugekyung/townbase/pull/38)로 완료했다. 리뷰 후속 변경은 [대응 기록](v0.2-c02-c03-review-response.md)을 따른다. ## 범위와 현재 상태

- C02: OpenAI answer/embedding Key를 AES-256-GCM으로 저장·교체·비활성화·삭제하고, 다른 요청/서비스 인스턴스/실제 API 재시작 후 마스킹 상태를 재조회한다. 원문이나 암호문·nonce·master 식별자를 API에 반환하지 않는다. 연결 상태는 항상 not_checked다.
- C03: 등록 문서 임베딩·RAG·일회성 첨부 전송 boolean을 각각 저장한다. 처음 행이 없으면 모두 false다. DB 최신 값을 읽는 내부 사전 검사와 고정 OpenAI endpoint·기본 로컬 비밀 패턴 검사를 제공한다.
- 답변 모델은 null이고 지원 목록은 빈 배열이다. 임베딩 text-embedding-3-small/1536은 읽기 전용이다. 임의 공급자·endpoint·모델/차원 변경 필드를 설정 요청에 넣으면 거절한다.
- 실제 연결 검사·답변 모델 선택/호출·토큰·가격표·비용 예약/정산은 C01/C04에서 구현·검증하기 전까지 비활성이다. 파일/질문/첨부의 실제 네트워크 경계에 사전 검사를 연결하는 것도 해당 후속 단계의 완료 조건이다. 현재 정책 검사 함수만으로 외부 호출 보호 전체를 완료했다고 표시하지 않는다.
- 새 설정 웹은 만들지 않았다. production 동일 origin API와 개발 Vite /settings 전달 경로만 추가했다. 인증·Origin/Host·JSON·no-store를 유지한다.

## 접근·재인증·저장

새 경로는 DeploymentModule 안의 ModelIntegrationModule을 통해 등록하며 AuthModule의 기본 인증 대상이다. 공개 예외를 추가하지 않는다. 서버가 DB에서 확인한 설치/관리자/워크스페이스를 사용하며 client ID는 신원으로 사용하지 않는다. 실제 API 계약은 [배포 안내10절](../self-hosted-deployment.md#10-key외부-전송-설정-api-c02c03-기반)을 따른다.

중요 변경은 매번 현재 비밀번호를 다시 확인한다. 비밀번호 형식 오류는400, 형식이 맞지만 틀린 비밀번호는401로 구분하며 두 경우 모두 시도 제한에 반영한다. S04의5분 재사용 상한보다 강한 즉시 확인이며 재인증 캐시/미래 권한 테이블을 추가하지 않는다. AuthenticationState 배타 잠금 아래 최신 세션·설치·활성 관리자·DB 시각을 확인한다. 비밀번호 실패는 기존 로그인 시도 제한에 실제 저장한다. Key/정책 쓰기·해당 종류의 감사 이벤트·세션 활동 갱신은 같은 트랜잭션이다. 작업 중 절대 만료·감사 실패·암호화 실패는 전체 취소한다. 공개 HTTP guard 이후 세션 폐기/만료가 발생해도 변경 전에 다시 거절한다.

ModelCredential은 installationId/purpose 복합 키이며 현재 암호문 하나만 저장한다. ModelTransferPolicy는 설치별 boolean만 저장한다. SQL CHECK는 primary 설치·암호화 형식/문자/길이를 제한하고 FK를 적용한다. 기존 설치/문서·대화/Agent 모델 설정을 위한 미래 테이블은 추가하지 않는다. 감사 action은 answer/embedding의 updated/disabled/deleted 및 정책 변경으로 구분하며 원문·Key 이력 payload를 만들지 않는다.

## 비밀 파일·암호화·복구

prepare가 별도의32-byte model_master_key를 만든다. 기존 값 보존, 정규 base64url 검사, 호스트 상위 폴더0700·파일0444를 적용한다. Compose는 API에만 읽기 전용 마운트하며 migration/DB에는 전달하지 않는다. DB 비밀번호를 암호화 키로 재사용하거나 환경의 다른 Key로 대체하지 않는다.

Vault는 별도 파일을 O_NOFOLLOW/O_NONBLOCK으로 열고 일반 파일·크기·읽기 전용 모드를 검사한다. 버전1·master fingerprint·설치·purpose를 GCM 추가 인증 데이터로 결합하며 암호화마다12-byte nonce를 새로 생성한다. master와 소유한 임시 평문 Buffer는 성공/인증 실패 모두 finally에서 정리한다. 반환 문자열이나 JavaScript 런타임의 모든 메모리 복사본 삭제를 보장하지 않는다. 읽을 때 형식/nonce/tag/base64·설치/용도·master 일치 및 인증 태그를 검증한다. Key 누락·오염·변조 시503의 고정 코드만 제공하며 master_key_unavailable/credential_unavailable/database_unavailable 등 허용된 진단으로 원인을 구분하고 비밀값/stack을 로그로 내보내지 않는다.

master는 DB 백업과 분리해 보호·보관해야 한다. 삭제 후 prepare로 새 파일을 만드는 것은 기존 암호문 복구가 아니다. 원래 master 복원 또는 운영자의 명시적 공급자 Key 재등록이 필요하다. 현재는 master 자동 회전·백업/복구 실행 기능을 제공하지 않는다. 비활성화는 현재 암호문을 유지하며 삭제는 현재 행을 없앤다. 없는 Key/이미 비활성 Key의 disable과 반복 delete는 실제 전이 때만 감사한다. 이미 저장된 동일 전송 정책도 다시 쓰거나 변경 감사로 기록하지 않는다. 기존 백업에 남은 암호문 정리는 I의 백업 보관 범위와 구분한다.

## 외부 전송 기반과 제한

로컬 검사만 수행하며 실제 provider HTTP 호출은 없다. document_embedding은 documentEmbedding, rag_question_embedding/rag_answer는 rag, attachment_answer는 attachment의 명시 true를 요구한다. 다른 목적을 허용 근거로 대신하지 않는다. endpoint는 정확한 https://api.openai.com/v1/embeddings 또는 /responses만 인정하고 사용자 입력 URL을 실행하지 않는다.

private key PEM·OpenAI Key·GitHub/Slack 토큰·명시 secret 환경 설정 패턴과 .env/인증 키 파일명을 로컬에서 검사한다. 일부 Unicode 정규화/숨은 문자 사례도 시험한다. 완전한 DLP·모든 비밀의 자동 탐지를 보장하지 않는다. 후속 호출은 이 검사뿐 아니라 자료 범위·활성 자격 증명·예산 예약을 실제 전송 직전에 확인해야 한다. 사전 검사 결과를 장시간 유효한 호출 권한으로 보관하지 않는다.

공식 자료 확인: [고정 임베딩/차원](https://developers.openai.com/api/docs/guides/embeddings), [공급자 데이터 보관](https://developers.openai.com/api/docs/guides/your-data). 향후 Responses의 store:false와 공급자 모든 보관 제거를 혼동하지 않는다. 최초 답변 모델 ID·API/계정 가용성·가격은 C01/C04에서 공식 문서와 합성 live 호출로 검증한 뒤 확정한다. 이번에는 실제 Key나 사내 문서를 보내지 않았다.

## DB 권한과 배포

제한 계정에 두 테이블 SELECT/INSERT, 명시된 암호문/활성·정책/updatedAt 열 UPDATE, ModelCredential DELETE만 추가한다. 두 테이블 installationId와 credential purpose/createdAt UPDATE, 정책/감사/관리자/자료 DELETE, 문서 읽기, DDL·sequence·권한 위임은 허용하지 않는다. 권한 검사 허용 목록도 같은 열을 기준으로 갱신하고 PUBLIC 우회는 계속 거절한다. readiness는 신규 테이블 조회 권한/존재도 검사하며 제품 전체·실모델 준비 완료로 표시하지 않는다.

업그레이드는 기존 설치 이름/포트/DB와 master를 보존한다. prepare로 추가 secret을 준비하고 최신 migration/제한 계정 설정 뒤 API를 재생성한다. root script·Compose 명령은 배포 안내를 따른다. 운영 DB에는 이 작업 중 migration을 적용하지 않았다.
