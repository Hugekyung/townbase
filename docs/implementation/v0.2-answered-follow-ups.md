# R07 답변에 추가 확인 항목 허용 (Q07·Q10)

2026-11-12. 구현·검증은 `codex/v02-answered-follow-ups` 브랜치의 로컬 기록이다. 실제 모델 재측정은 이번 변경에 포함하지 않았다(아래 「남은 확인」). 커밋·푸시·PR은 사용자 승인 전에는 하지 않는다.

## 문제

- 2026-11-11 15문항 측정(`main` `74abc42`, 새 대화)에서 Q07이 `TOWNBASE_RAG_GROUNDING_ANSWERABILITY`로 실패했다.
- 근거 예산 확장 뒤 측정(`main` `8241059`, 한 대화에서 이전 대화 참고 사용)에서는 Q10이 같은 코드로 실패했다.
- 두 질문 모두 정답에 사용자가 직접 확인할 항목이 들어간다. Q07은 "나머지 요건 확인", Q10은 "접수 장소가 두 곳으로 달라 확인 필요"다.
- R05 v2 규칙은 답변 가능(`isAnswerable=true`)이면 `reason`이 비어 있고 `followUps`도 비어 있어야 했다. 이 진단 코드는 세 경우를 한데 묶어 기록한다. 답변 가능인데 `followUps`가 있는 경우, 답변 가능인데 `reason`이 있는 경우, 답변 가능인데 사실이 없는 경우다.
- 공급자 원문은 저장하지 않으므로 둘 중 어느 쪽을 어겼는지는 확인할 수 없다. 다만 지침이 이미 `followUps []`를 명시하고 있었고, 정답 형태가 "답 + 확인할 점"이므로 `followUps` 쪽일 가능성이 높다.
- 어느 쪽이든 결과 전체가 기술 실패(`invalid_grounded_response`)로 끝나, 사실이 맞아도 0점이 된다.

## 변경

- `parseGrounded` v2(`apps/api/src/rag/rag-policy.ts`): 답변 가능 결과도 `followUps`를 가질 수 있다.
  - 항목은 최대 5개·각 300자이고, 제어 문자를 허용하지 않는다. 사실이나 인용을 담지 않는다는 제한도 그대로다.
  - 모든 사실은 계속 claims에 넣고 정확 인용 검증을 받는다.
- 답변 가능인데 `reason`이 비어 있지 않으면 계속 거절한다. 진단 코드는 새 `answerable_reason`(`TOWNBASE_RAG_GROUNDING_ANSWERABLE_REASON`)이다.
  - 같은 실패가 다시 나면 어떤 규칙을 어겼는지 구분할 수 있다.
  - 사실 없는 답변과 사유 없는 거절은 기존 `answerability`다. 공개 오류 코드는 그대로 `invalid_grounded_response`다.
- RAG v2 지침: `Answerable: reason "" and followUps [].`를 `Answerable: reason ""; followUps only for user-side checks.`로 바꿨다.
  - 최소 입력 설정 4,096에서 짧은 출처 프롬프트가 들어가도록 다른 두 문구를 같은 뜻으로 줄였다(`Answer directly stated facts …`, `(max 5 short Korean items; no facts/citations)`).
  - 시험 기준 여유는 약 4B다. 지침을 더 늘리려면 이 시험부터 확인한다.
- 화면: 서버의 `answerText`가 이미 `추가로 확인할 항목:` 목록을 붙인다. 답변이면 거절 안내(범위 문구·"일부 근거만 확인")를 붙이지 않는다. 웹은 바꾸지 않았다.
- 바꾸지 않은 것:
  - Gap은 거절 결과에만 저장한다.
  - 응답 schema(`townbase_rag_grounded_v2`)는 그대로다.
  - 첨부 v1 계약과 지침도 그대로다.
- 저장 결과 재조회도 같은 규칙으로 읽는다. 이전 v2 행은 답변이면 `followUps`가 비어 있으므로 그대로 읽힌다.

## 검증

- `rag-answer-contract.spec.ts`
  - 답변 가능 + `followUps`가 받아들여지는지 확인한다. 화면 문자열은 사실·출처 다음에 확인 항목이 붙고, 거절 안내는 붙지 않는다. 저장 행 재조회도 확인한다.
  - 답변 가능 + `reason`이 `followUps` 유무와 관계없이 `answerable_reason`으로 거절되는지 확인한다.
  - 사실 없는 답변은 `followUps`가 있어도 `answerability`로 거절되는지 확인한다.
  - 답변의 `followUps`도 5개 제한을 지키는지 확인한다.
  - v2 지침 문구가 바뀌었는지, v1 지침에 `followUps`가 없는지 확인한다.
- 수정 전 코드에서 새 시험 5개가 실패함을 확인했다. 5개 제한 시험은 변경 전후 모두 통과하는 보호 시험이다.
- `pnpm lint`, `pnpm build`, `pnpm test`(734개 통과, opt-in DB suite 334개 건너뜀), `pnpm test:deployment`(53개) 통과.
- RAG 실 DB suite와 실계정 모델 호출은 실행하지 않았다.

## 남은 확인

- 병합 후 API만 다시 빌드한다. 이후 Q07·Q10을 질문마다 새 대화로 재측정한다.
- 모델이 확인 항목을 불필요하게 늘리지 않는지, 직접 적힌 사실에 "확인 필요"를 붙이지 않는지 함께 본다. 지침은 직접 적힌 사실은 확인을 요구하지 않고 답하라고 유지한다.
- 다시 실패하면 진단 코드로 `reason` 문제(`ANSWERABLE_REASON`)인지 다른 규칙인지 구분한다.
