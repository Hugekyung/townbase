# v0.2 RAG 검색·근거·답변 품질 개선 계획

작성일: 2026-11-10
상태: 묶음 A의 검색·페이지/문단 분할 기반은 로컬 검증·반영 완료. R04-b 표 구조 검증·보완과 묶음 B는 미완료. 도입 문서 재색인은 미실행이며 답변 점수 재측정은 사용자가 직접 수행.
목적: 행복주택 PDF 도입 시험에서 드러난 검색 누락과 근거 전달 문제를 해결한다. 모델 교체보다 원인 분리와 재현 가능한 검증을 먼저 한다.

후속 지시(2026-11-10): 묶음 A는 [구현 기록](v0.2-rag-quality-improvement.md)의 로컬 반영·검증까지 진행했다. 사용자가 실제 답변 점수 재측정은 모든 개선 후 직접 수행한다고 정했으므로 R07의 실계정 모델/effort 비교·답변 재평가는 자동 수행하지 않는다. 해당 절은 검증 설계 참고로 보존하며, 에이전트가 실행할 필수 작업으로 취급하지 않는다. 사용자는 현재 변경의 커밋·푸시·main 대상 PR 생성을 승인했다.

## 1. 기준과 작업 경계

- 제품 기준: [기본 PRD](../../PRD_v0_2_self_hosted_agent.md) B05~B10·출처 답변·거절·Gap, [TASK](../../TASK_v0_2_self_hosted_agent.md) D04/D05·E02~E04·J, [선택 기록](../../DECISIONS_v0_2_basic.md) S02·S10~S14.
- 이 문서는 기존 기능의 품질 개선 계획이다. 완료된 TASK나 과거 평가 결과를 소급 수정하지 않는다. 구현 시 현재 계약이 달라지는 항목만 PRD/TASK/DECISIONS/AGENTS와 함께 갱신한다.
- 단일 설치·관리자, 고정 임베딩 `text-embedding-3-small`/1536, 기존 retrieval mode, ModelExecutionService의 전송·비용·요청 ID 경계를 유지한다.
- 새 검색 서버·worker·범용 플러그인·OCR·전체 코드 색인·새 문서 서비스는 추가하지 않는다. 우선 기존 PostgreSQL과 API 안에서 해결한다.
- 첨부와 일반 RAG를 분리한다. 첨부 본문·후속 대화·파생 질문을 검색 임베딩이나 공용 평가 데이터에 넣지 않는다.
- 계획 작성은 문서 작업이므로 브랜치를 새로 만들지 않는다. 코드 착수 전 별도 `codex/` 작업 브랜치를 마련한다. 기존 미커밋 채팅 설정·사용량·연결 안정성 변경은 보존하고, 기준 커밋/로컬 차이를 먼저 기록한다. 무단 stash/reset/cherry-pick 또는 기존 변경의 혼합 커밋을 하지 않는다.
- 이번 요청은 계획 저장까지다. 실제 도입 DB 변경·재색인·유료 호출·커밋·푸시·PR 생성 권한으로 확대 해석하지 않는다.

### 2.2 코드에서 확인된 원인과 가설

1. **확인: 근거 예산의 구조적 병목.** `file-chunker.ts`의 조각 상한은 4096 UTF-8 bytes이고 `rag-policy.ts`의 8000-byte 한도는 메타데이터를 포함한 배열 JSON에 적용된다. 4096-byte 조각 2개는 본문만으로도 8192 bytes다. 최대 5개라는 개수 설정만으로 복수 근거 전달을 보장할 수 없다.
2. **확인: 검색은 vector 후보20개가 출발점.** `FileIndexService.search`에서 cosine 거리 순으로 후보를 가져온다. `lexicalEvidence`는 그 후보 안의 재정렬/판정일 뿐 독립 어휘 검색이 아니다.
3. **확인: 분할은 바이트 경계이며 overlap이 없다.** 표/문단/페이지/예외가 갈라질 수 있고 PDF headingPath는 빈 배열이다. 테이블 문자 일부가 저장되어 있음을 확인했지만 전체 셀 연결의 정확성은 아직 검증하지 않았다.
4. **확인: 답변 계약의 제한.** false 응답은 claims를 허용하지 않고 reason에는 인용 연결이 없다. conflicts는 다른 originalId 2개를 요구해 동일 PDF 내부 충돌을 표현하기 어렵다.
5. **미확정: Q08의 정확한 검증 실패 분기.** 현재 기록은 공통 오류 코드만 있어 JSON 형식/출처 ID/인용 불일치/결과 불변식 중 어느 것인지 알 수 없다. 관련 페이지 일부가 선택됐다는 사실만으로 인용 오류를 확정하지 않는다.
6. **미확정: 당시 후보별 순위와 탈락 원인.** 최종 선택 근거는 저장되지만 전체 후보/탈락 이유/질의 벡터는 없다. 과거 vector 순위를 복원했다고 주장하지 않는다.
7. **미확정: 모델과 임베딩의 독립 품질.** 잘못된 근거로 실패한 결과만으로 모델 교체 효과를 판단하지 않는다.

## 3. 구현 묶음과 순서

두 묶음으로 진행하되 내부 검증 지점은 유지한다. 한 번에 전체 로컬 구현을 진행하더라도 단계별 증거를 남기고 마지막에 요약 후 전달 승인을 받는다.

| 묶음 | 작업 | 의존/종료 기준 |
| --- | --- | --- |
| A: 검색·근거 | R01 재현/진단 → R02 근거 패킷 → R03 복합 검색 → R04 문서 구조/재색인 | 정답 사실이 저장된 위치에서 최종 모델 입력까지 전달되는 것을 입증 |
| B: 답변·품질 | R05 계약/인용/충돌 → R06 통합 회귀 → R07 실제 모델 비교 | 오류·과도한 거절·잘못된 출처를 줄이고 보호·비용·지연 기준 충족 |

R05의 세부 진단은 R01과 함께 시작할 수 있다. 모델 교체 여부 판단은 R02~R06 완료 후에만 한다.

## 4. R01 — 기준선 고정과 원인별 진단 (P0)

**수정 대상:** `apps/api/src/rag/rag.service.ts`, `rag-policy.ts`, `apps/api/src/files/file-index.service.ts`, `apps/api/test/rag-policy.spec.ts`, 평가 실행기/fixture.

1. Q01~Q15의 실제 질문 문자열·필수 사실·정답 조건·근거 범위·답변 가능 상태를 버전 있는 fixture로 고정한다. 이번 대화의 원 질문을 그대로 사용하고 아래 표는 채점 계약으로 사용한다.
2. 기준선에는 소스 커밋과 미커밋 차이의 hash, API compiled hash, PDF SHA-256, 추출/색인 configurationVersion, 모델/effort/한도, 독립/이력 포함 여부를 기록한다. PDF 페이지가 같아도 질문에 해당하는 조항이 다르면 오답으로 처리한다.
3. 검색 trace는 후보 ID·raw score·어휘/의미 순위·최종 순위·채택/탈락 이유·본문/패킷 bytes·실제 선택 수·검색 구간 시간을 구분한다. `threshold`, `budget`, `count`, `scope` 등의 이유를 구분한다. 모델 답변을 실행하지 않은 경우도 명시한다.
4. 검증 오류는 허용된 내부 진단 코드로 분리한다: JSON/schema, source ID, quote 불일치, answerability 불변식, conflict 근거 부족 등. 기존 공개 오류의 호환성은 유지하고 원문 공급자 응답을 공용 로그에 남기지 않는다.
5. 진단은 우선 opt-in 평가 실행기의 소유자 전용 로컬 JSON artifact로 저장하고 다시 읽어 검증한다. 키·세션·공급자 원문·질의 벡터를 저장하지 않으며 문서 본문 복제를 피한다. 원본 접근이 무효해진 뒤 trace를 이용해 본문을 복구하지 못하게 한다. 운영 기본 trace 저장 테이블은 선개발하지 않는다.
6. 평가 디렉터리는 버전 관리되는 명세/합성 fixture와 로컬 실문서 관측물을 분리한다. 사용자 대화나 원본 PDF를 자동으로 저장소 fixture에 복사하지 않는다. 공개 배포 자료라도 필요한 인용/출처/사용 범위를 확인한다.

**종료:** 하나의 실패 fixture에서 저장→별도 읽기까지 trace가 일치하고, 각 차단 분기가 다른 조건 없이 독립 재현된다. Q08의 원래 실패 분기는 미확정으로 남기며 후속 재현 결과를 별도 기록한다.

## 5. R02 — 8KB 안의 복수 근거 패킷 (P0)

**수정 대상:** `rag-policy.ts`, `rag.service.ts`, `rag-store.ts`, `file-source.ts`, `rag-policy.spec.ts`, `rag.integration.spec.ts`.

1. 선택용 DB 행/접근 메타데이터와 모델 전달용 source DTO를 분리한다. 모델에는 S번호·제목·필요한 위치·실제 근거 본문만 보내고 저장/참조에 필요한 식별 값은 서버에서 유지한다.
2. **초기 8000 UTF-8-byte 근거 한도는 유지한다.** 실제 전송하는 source JSON 전체에 적용하고 전체 instructions/input/format은 기존 `inputBound`·설치 입력 한도·비용 예약을 모두 통과해야 한다. 모델이 허용하는 context 크기와 제품 한도를 혼동하지 않는다.
3. 완전한 4096-byte 조각만 선택하는 계약을 완전한 **근거 단위** 선택으로 변경한다. 단위는 완결 문장/번호 문단/표 머리글을 포함한 행이다. 중간 글자나 금액을 잘라 넣지 않는다. 큰 단위가 한도 안에 못 들어가면 명시적으로 미포함 처리한다.
4. 최대 source 5개를 유지하고 중복 단위를 제거한다. 질문의 항목별 근거가 골고루 포함되는지 추적한다. 개수만 늘리고 같은 내용으로 채우지 않는다.
5. 근거 단위마다 원래 chunk ID/hash, 정확한 본문 offset, 원본 위치를 연결한다. 서버는 실제 전송한 excerpt에서 인용을 검증한다. 보내지 않은 원 chunk의 문장으로 인용 검증을 통과시키지 않는다.
6. Q02처럼 표와 전환 규칙, Q08처럼 가산 규칙과 금액표를 함께 포장한다. 한도 때문에 필요한 근거가 빠지면 원인을 진단에 남기고 완전 답변으로 가장하지 않는다.
7. source 개수 증가에 따라 이력+현재 출처 최대20 경계도 검증한다. 과거 응답의 저장/재조회는 그대로 유지한다.

**종료:** 두 개 이상 근거를 담는 실제 직렬화 시험, 7999/8000/8001-byte·한글/이스케이프·긴 제목 경계, 낮은 설치 입력 한도, 이력 포함 입력 초과 시험 통과. 새 source/excerpt 저장 형태는 기존 저장 결과와 구분하고 호환 재조회 시험을 둔다. PRD/TASK/DECISIONS의 ‘완전 조각’ 표현도 이 계약과 함께 갱신한다.

## 6. R03 — 의미 검색과 어휘 검색 결합 (P1)

**수정 대상:** `file-index.service.ts`, `rag-policy.ts`, `rag.service.ts`, 필요시 `packages/rag-core/src/`의 작은 공통 helper. 기존 mode의 legacy 회귀는 보존한다.

1. 동일한 권한/최신 색인 조건을 쓰는 독립 어휘 검색을 추가한다. 초기에는 의미 후보20·어휘 후보20의 합집합 최대40개를 내부 후보로 삼고 최종 근거5개는 유지한다.
2. `화수정원마을`, `1단지`, `18형`, `청년`, `소득有`, `계약금`, `실제 근무지`, `갱신계약` 등 항목명·숫자·복합어를 보존한다. 일반 불용어와 조사를 처리하되 `또는`, `이하`, 부정어 같은 의미 조건을 근거에서 제거하지 않는다.
3. 한국어 검색을 PostgreSQL 기본 언어 분석만으로 충분하다고 가정하지 않는다. 초기 구현은 매개변수화한 정규화 문자열/항목 일치로 후보를 만들고, 규모 시험에서 필요가 확인될 때만 인덱스/확장을 추가한다. 동적 SQL 문자열 연결이나 외부 형태소 서버는 추가하지 않는다.
4. 의미·어휘 순위는 RRF 방식의 순위 결합(초기 동등 가중·k=60)으로 합친다. 이 값은 검증할 시작점이지 품질 보장이 아니다. raw cosine·어휘 score·결합 score를 분리하고 결합 점수를 기존 cosine threshold와 비교하지 않는다.
5. 정렬과 별개로 답변 가능 사전 판정을 재검토한다. metadata 가산점으로 사실 근거를 인정하지 않는다. 상위3 평균 때문에 실제 정답 조각을 버리는 사례를 fixture로 고정하고, 정답 조항 존재/선택 실패/실제 근거 부족을 분리한다.
6. 긴 질문의 단어 수 초과로 어휘 검사 전체가 꺼지는 현재 분기를 없앨 때는 제한된 항목 추출·처리 시간 상한을 함께 둔다. 질문을 임의로 전부 단어 AND 조건에 넣지 않는다.
7. 관련 앞뒤 단위 확장은 같은 원본/버전/scope 및 인증·전송 경계를 다시 거친다. 다른 문서나 제외된 자료를 확장으로 끼워 넣지 않는다. 원본 하나가 후보를 독점하지 않도록 중복 내용과 단위를 제어한다.

**종료:** Q01/Q03/Q06/Q09/Q13의 정답 조항 선택 확인, 숫자/조사/띄어쓰기 변형·같은 금액의 다른 계층·근거 없는 키워드 질문 회귀 통과. 검색 지연은 공급자 임베딩 시간을 제외하고 계측한다.

참고: [pgvector 공식 Hybrid Search 안내](https://github.com/pgvector/pgvector#hybrid-search). 외부 문서는 접근/삭제/전송 경계를 대신하지 않는다.

## 7. R04 — 구조를 보존하는 분할과 재색인 (P1)

**수정 대상:** `file-parser.ts`, `file-chunker.ts`, `file-index.service.ts`, `file-index-state.ts`, `file-run.service.ts`, 관련 단위/통합 시험.

1. 먼저 기존 추출문 위에서 제목·번호 문단·문장 경계를 보존하도록 분할한다. 조각 최대4096 bytes는 유지하고 인접 문맥 overlap은 최대512 bytes의 완전 단위로 제한한다. overlap으로 추가된 본문도 embedding bytes·보관·출처 범위에 포함한다.
2. PDF 표는 텍스트 항목 좌표와 행/열 구조를 검토해 머리글·단위·행 이름이 붙은 근거 단위로 만든다. 병합 셀은 시각 원문과 대조하고 확신 없는 연결은 추측하지 않는다. 행복주택 전용 금액/행을 하드코딩하지 않는다.
3. 단순 분할 수정으로 해결되지 않는 표만 파서 개선으로 진행한다. 원 추출과 정규화 본문 간 offset/좌표 연결을 남기고 인용/페이지 참조가 재현돼야 한다. PDF 출력 순서가 곧 시각적 읽기 순서라고 가정하지 않는다.
4. `FILE_INDEX_CONFIGURATION`을 새 버전으로 구분한다. 기존 index가 존재할 때 `unchanged`로 끝나는 조건, 새 configuration의 교체 허용, FileRun fingerprint/재시도/완료 조건, 이전 출처 유효성 판정을 함께 확인한다.
5. 새 색인은 별도 격리 DB/자료에서 생성·검증한 뒤 명시 수동 작업으로 도입 문서에 적용한다. 전환은 불완전 새 색인을 공개하지 않는 원자적 경계로 처리한다. 실패/중단/재시작 시 기존 유효 색인의 보존 또는 차단 상태를 명확히 하며 조용한 부분 색인을 금지한다.
6. 기존 schema 제약 때문에 필요한 경우에만 전진 migration과 좁은 runtime 권한을 추가한다. 기존 migration 재작성·db push·임의 운영 reset은 금지한다. 운영 재색인 전 비용 추정·백업·복구 절차를 제시한다.
7. PDF 외 DOCX/MD/TXT의 heading/location 계약, 기존 메타데이터, 20MiB/30만자/30초/파서 자원 상한을 유지한다. 구조 분석이 상한을 넘으면 명시 실패한다.

**종료:** 표 머리글/단위/계층 경계, 페이지 경계, 긴 한 문장, 병합 셀, 파일 말미, 중복 overlap 시험과 새/옛 설정 업그레이드·실패 복구 readback 통과. 기존 인용 결과를 소급 변경하지 않는다.

## 8. R05 — 부분 근거·정보 부족·동일 문서 충돌 (P1)

**수정 대상:** `rag-policy.ts`, `rag-store.ts`, `model-integration/grounded-format.ts`, `packages/agent-core/` 계약, `apps/web/src/workspace/ChatPanel.tsx` 및 결과 타입/출처 표시. 첨부 계약 소비자도 함께 검사한다.

1. `isAnswerable`은 사용자가 요청한 최종 판단을 할 수 있는지로 유지한다. false여도 검증된 일부 사실을 별도 supporting claims로 설명하고, 부족한 입력은 follow-up 항목으로 구분한다. 확인된 일부 사실을 최종 자격 승인으로 표현하지 않는다.
2. RAG용 v2 결과 계약을 버전으로 구분한다. 기존 v1 저장 행은 기존 parser로 재조회하고 새 응답만 v2로 검증한다. 기존 공용 format을 쓰는 첨부를 무심코 변경하지 않도록 RAG purpose별 format을 분리한다.
3. false의 지원 사실도 S번호/정확 인용 검증을 필수로 한다. `reason`/추가 질문은 사실 근거를 우회하는 서술 통로가 아니어야 한다. ‘이번에 찾지 못함’과 ‘문서 전체에 없음’을 구분한다.
4. conflict는 다른 문서 또는 같은 문서의 서로 다른 근거 구간 최소2개를 허용한다. 같은 구간 중복·겹친 chunk의 동일 문장 2개는 양쪽 근거로 인정하지 않는다. 같은 chunk에 상충 구간이 있는 경우도 위치/offset으로 구분한다.
5. Q10은 16쪽과17쪽의 장소/출구 양쪽을 인용하고 확정을 유보한다. Q14는 알려진 연령 조건과 미확인 혼인·무주택·세대/소득·자산 등 추가 확인 사항을 구분한다. Q15는 날짜는 모른다고 하되 대기/공가 규정을 인용한다.
6. `refused` 상태·Gap 생성·answer model 필수 여부·DB CHECK·웹 배지·이력/첨부 타입을 함께 검토한다. 부분 근거를 answered로 세어 성공률을 높이지 않는다. Gap은 실제 미해결 질문에 대해 저장하고 별도 조회한다. 기술 오류는 Gap 성공으로 세지 않는다.
7. 정확 인용 원칙을 유지한다. 잘못된 숫자/출처를 유사 문자열로 자동 보정하지 않는다. 유료 자동 재시도/자동 상위 모델 전환 없이 최초 실패와 진단을 보존한다.

**종료:** v1/v2 저장·별도 재조회, 잘못된 quote/ID/같은 근거 중복 충돌 차단, false+검증 사실+추가 질문 표시, 실제 Gap readback, 첨부 기존 계약·보관·격리 회귀 통과.

## 10. R06 — 검증 순서와 완료 기준

### 10.1 세 층으로 원인 분리

1. **추출/검색 시험:** 공급자 없이 합성 vector·실제 추출 fixture로 저장 위치/선택 근거/권한을 검증한다. 합성 vector 성적을 실제 의미 검색 품질로 보고하지 않는다.
2. **정답 근거 직접 제공 시험:** 사람이 확인한 정답 excerpt를 모델에 제공해 해석·계산·인용만 측정한다. 이것은 검색 성공률이 아니다.
3. **제품 전체 시험:** 새 대화·이력 없음으로 업로드→추출→색인→검색→답변→저장→별도 재조회까지 측정한다. 추가로 동일 대화 후속 질문을 별도 집합으로 시험한다.

### 10.2 필수 자동/DB 시험

- 우선 `file-chunker.spec.ts`, `rag-policy.spec.ts`와 새 source selection/validation 단위 시험을 실행한다. build 산출물을 소비하는 시험 전 `pnpm db:generate`와 `pnpm build`를 수행한다.
- 전체 `pnpm lint`, `pnpm test`, `pnpm db:validate`, 변경 영향에 따른 `pnpm connectors:build`/`pnpm connectors:test`, `pnpm test:deployment`를 실행한다. DB 없는 database/connector 시험은 `--testPathIgnorePatterns=integration.spec.ts`로 통합 suite 전체를 제외한다.
- DB 통합은 기존 suite의 정확한 guard를 유지한다. RAG `TOWNBASE_RAG_TEST=1`/`postgres/townbase_e02_test`, 파일 색인 suite의 실제 guard는 착수 전 파일에서 확인한다. 권한 suite는 `townbase_pr34_*_test`만 허용한다. 현재 도입 DB를 테스트 reset 대상으로 사용하지 않는다.
- 신규 열/JSON 계약/migration이 있으면 새 설치·구버전 업그레이드·기존 대화 보존·제한 계정 허용/비허용 열을 실제 DB로 검증한다. 정책/로그아웃/삭제/교체/제외가 후보 조회 뒤·모델 전송 전·게시 전 일어난 경우 모두 차단한다.
- 후보/근거 확장으로 제외 자료가 다시 유입되지 않아야 한다. 첨부 canary가 공용 색인·Gap·진단 artifact에 자동 전파되지 않아야 한다.
- 웹에서는 출처 번호/정확한 구간/부분 판단/추가 질문/동일 문서 충돌/기술 실패/과거 v1 결과를 실제 응답으로 확인한다. 불필요한 새 운영 설정 화면은 만들지 않는다.

## 11. R07 — 실제 모델 비교와 도입 환경 적용 (P2)

1. 기존 승인 모델과 고정 임베딩을 유지한 채 R02~R06의 무과금 시험을 먼저 마친다. 사용자의 기존 유료 시험 승인은 합성 입력/상한/당시 범위를 넘겨 재사용하지 않는다.
2. 실제 호출 전 이번 PDF/질문 전송 범위, 사용할 계정/Key, 모델·effort 비교 조합, 재색인 포함 여부, 최대 호출 수와 총 비용 상한을 구체적으로 산정한다. 필요한 새 실행 권한이 없으면 이 단계만 대기하고 나머지 구현은 마친다.
3. 정답 근거 직접 제공과 실제 검색 조건을 분리하고, 승인된 같은 질문/근거/한도에서 Luna low와 기존 상위 옵션을 비교한다. 모델·effort를 동시에 바꾸지 않는다. 출력/추론 토큰 한도·usage·latency·비용도 기록한다.
4. 정답 근거 직접 제공은 성공하지만 실제 검색은 실패하면 검색 개선을 계속한다. 동일 근거에서도 해석/표 계산/인용 실패가 반복되고 상위 옵션의 개선이 재현될 때만 기본 모델/effort 변경을 별도 제안한다. 임베딩 large 전환은 이 계획에서 하지 않는다.
5. 도입 문서 재색인 전 백업과 복구 경로를 확인한다. 재색인은 사용자에게 대상/비용/예상 영향이 명확한 명시 수동 실행으로 진행한다. 자료가 바뀌면 새 실행 UUID와 provenance를 사용하고 이전 유료 실패 ID를 자동 재전송하지 않는다.
6. 배포 후 Q01/Q02/Q08/Q10/Q13/Q14/Q15를 먼저 확인하고 전체15문항으로 확장한다. 불완전 색인/보호 회귀/오답이 확인되면 신규 색인 전환을 중단한다. 이미 무효화된 문서나 예전 scope를 복구 명목으로 되살리지 않는다.
