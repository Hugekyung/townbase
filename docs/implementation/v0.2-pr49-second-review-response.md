과거 잠금 진단은 사용한 script hash와 raw log를 그대로 보존한다. 당시 runner는 `lock-recycling-runner.historical.txt`로 보관하고 기존 `scriptSha256`의 대상을 이 파일로 연결했다. 현재 재현용 `.mjs`와 별도의 hash를 추가했으며 과거 측정을 새 runner로 실행한 것처럼 기록하지 않았다.

## 검증

- API 전체 640개 통과, 기존 opt-in DB 331개 제외.
- 배포/프록시 43개 통과. 새 잠금 진단 3개는 이 수에 포함하며 다시 더하지 않는다.
- 실제 Docker 종료 통합 시험 1개 통과. **중복 제외 684개**이며 이전 906개를 합산하지 않는다. 이번 수정은 DB schema/운영 SQL을 바꾸지 않아 기존 DB 통합 suite는 재실행하지 않았다.
- API build·lint·git diff 공백 검사 통과. 답변 점수 재측정·유료 API 호출·문서 재색인은 0회다.
- 배포 첫 실행은 기존 백업 시험의 Node fixture가 300ms 안에 PID 파일을 쓰지 못해 실패했다. 분리 실행은 통과했고, 시험용 deadline을 2,000ms로 조정해 시작 여유를 주었다. deadline 거절·실제 프로세스 종료 확인은 그대로 유지하며 제품 백업 제한은 변경하지 않았다. 최종 전체 배포 시험은 통과했다.

실제 종료 시험은 현재 Compose의 60초 설정을 읽고 데이터/Key/DB 연결 없이 `--network none`의 임시 컨테이너를 실행했다. 런타임 helper의 hash가 현재 build와 같은지 확인한 뒤 SIGTERM을 보냈고, 약 **45.092초에 exit(1)** 및 `TOWNBASE_FILE_SHUTDOWN_DEADLINE`을 확인했다. Docker SIGKILL의 exit 137이 아니며 임시 컨테이너는 finally에서 제거했다. 현재 `townbase-local`도 60초로 재생성한 후 readyz HTTP 200·DB/schema/storage/execution ready를 확인했다.

[검증 수치·hash·실제 종료 측정](evidence/v0.2-rag-retrieval/pr49-second-review-response.json)을 따른다. 이 시험은 파일 종료와 Compose의 유예 관계를 검증하며 모든 장애 상황·모델 품질을 보장하는 결과가 아니다.

## 명시 실행

기존 로컬 설치 준비 파일 `.townbase/compose.env`, 현재 소스의 API build, 동일 helper가 들어 있는 로컬 runtime 이미지가 필요하다. 프로젝트 루트에서 실행한다. DB/문서/secret을 시험 컨테이너에 마운트하지 않는다.

```sh
TOWNBASE_SHUTDOWN_DOCKER_TEST=1 TOWNBASE_SHUTDOWN_IMAGE=townbase-local-api node deployment/test/file-shutdown.integration.mjs
```

일반 `pnpm test:deployment`에는 이 실제 Docker 시험이 포함되지 않는다. 종료 유예는 기본 Compose 설정이며 운영자가 `docker stop -t` 등으로 더 짧은 시간을 명시하면 그 운영자 설정이 우선한다.

## 후속 리뷰 2건 (기준 `2ea8ac9`)

| 리뷰 | 변경과 근거 |
| --- | --- |
| 잠금 진단 client 종료 | `finally`의 `Promise.all`을 `Promise.allSettled`로 바꿨다. 한 client의 `$disconnect()` 실패가 원래 오류(`TOWNBASE_DIAGNOSTIC_LOCK_BUSY` 등)를 대체하지 않고, 모든 client의 종료를 기다린다. 첫 client 종료 실패와 두 번째 잠금 충돌을 함께 만든 시험을 추가했다. 이 시험은 이전 runner에서 `synthetic_disconnect_failure`로 실패하고 수정 후 통과한다. |
| Docker 종료 시험 정리 | `finally`의 `docker rm -f` 실패를 별도 고정 코드 `TOWNBASE_SHUTDOWN_CLEANUP_FAILED`와 실패 종료 코드로 보고하고, 원래 시험 실패는 대체하지 않는다. 정리 실패를 성공으로 숨기지 않는다. 로컬 Docker 29.8.2에서 없는 컨테이너의 `rm -f`는 exit 0이었으므로, 이 경로는 daemon 장애·시간 초과 같은 정리 자체의 실패에 해당한다. |

검증: 배포/프록시 44개 통과(새 잠금 진단 시험 1개 포함). 실제 Docker 종료 opt-in 시험 1개 통과(약 45.067초, exit 1, `TOWNBASE_FILE_SHUTDOWN_DEADLINE`, 임시 컨테이너 0개 잔존). 정리 실패 분기 자체는 daemon 장애를 재현하지 않아 실행 관측하지 않았다. 재현용 runner의 hash는 `lock-recycling-comparison.json`에서 갱신했으며, 이전 hash와 과거 측정 기록은 보존한다. 제품 코드·DB schema·유료 호출 변경은 없다.
