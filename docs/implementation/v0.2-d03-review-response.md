기존 적용 migration은 수정하지 않고 `20261031010000_file_run_contracts`로 제약을 강화한다. 잘못 연결된 기존 행은 migration을 실패시키며 데이터를 자동 수정/삭제하지 않는다. 정상 기존 원본·버전·추출·실행·요청 별칭은 실제 migrate runner 전후 모든 열/JSON으로 비교한다.

실패한 재처리의 마지막 성공 추출을 보존해도 새 실행을 성공으로 표시하지 않는다. 실행/추출 이력의 최신 실패 상태는 그대로 반환한다. D04 검색/벡터 색인은 이번 범위가 아니며 searchable=false를 유지한다.

## 검증 기록

- 중복 제외 자동 **572개 통과**: API420·배포24·D03 실제 DB34·D02 실제 DB26·runtime 권한68. 일반 API의8개 opt-in suite/190문항은 건너뛰었고 D02/D03/권한 시험은 별도 실행했다. 최초557개에 더해 총량을 부풀리지 않는다.
- `pnpm db:generate`, `pnpm build`, `pnpm lint`, `pnpm db:validate`, `git diff --check` 통과. API/배포의 HTTP 시험은 loopback 바인딩 허용 환경에서 실행했다. 처음 제한 환경의 EPERM 실패는 제품 실패로 계산하지 않으며 최종 허용 환경 결과로 대체했다.
- D03는 최종 Linux migration/build 이미지의 compiled API·실제 파서·제한 runtime 계정으로 실행했다. 최신 시험 소스만 해당 이미지에 읽기 전용 마운트했다. D02도 같은 최종 이미지에서 회귀했다. production runtime 이미지 전체 재시작을 이번 후속 변경으로 다시 검증했다고 주장하지 않는다.
- D03 이전이 아닌 **PR #43 초기 D03 schema/행**을 만든 별도 합성 upgrade DB에서 후속 migration을 실제 migrate runner로 적용했다. 원본·버전·추출 이력·FileRun·FileRunRequest의 모든 열/JSON을 비교해 그대로 보존됨을 확인했다. 이 수동 검증은572개에 합산하지 않는다.
- 첫 DB 실행에서 관계 거절 자체는 성공했으나, 실행 결과의 inputKey가 정상 비동기 정리로 NULL이 되는 것을 전체 행 불변으로 비교한3개 시험이 실패했다. 이후 비교를 해당 관계/상태 열로 한정해 정리와 독립 검증했다. 코드·잠금 보완 후 최종 D03/D02 전체를 새 임시 fixture에서 재실행해 통과했다.
- `/tmp/townbase-pr43-{api-final,deployment,d03-final,d02-final,acl-final,upgrade-final,build,lint-final,schema,image}.log`와 `/tmp/townbase-pr43-{docker-check.py,upgrade.mjs}`가 로컬 증거다. 이번 전용 `townbase-pr43-postgres` tmpfs 안의 guard 대상 DB만 사용했다. suite 자체는 reset하지 않으며 개발 재실행 시 이번 전용 DB만 명시 재생성했다. 기존/live DB·유료 모델 호출은 사용하지 않았다. 시험 후 전용 컨테이너·네트워크·합성 비밀 파일은 제거한다.
