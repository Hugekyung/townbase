## 제공 범위

- `POST /auth/login`: 관리자 이름·비밀번호 검사, 기존 cookie 세션 회전, 서버 저장 세션 발급.
- `GET /auth/session`: 현재 관리자·설치·만료 검사와 활동 시각 갱신. 사용자 이름과 절대 만료만 반환.
- `POST /auth/logout`: 현재 세션 폐기, 브라우저 cookie 삭제.
- `POST /auth/password`: 현재 비밀번호를 다시 검사하고 새 비밀번호 저장. 해당 설치의 모든 세션과 미사용 복구 토큰 무효화.
- `POST /auth/recover`: 서버 로컬에서 발급한 토큰으로 비밀번호 교체. 모든 기존 세션을 폐기하고 재로그인 요구.
- 서버 로컬 `node deployment/recovery.mjs`: 이미 초기화된 활성 관리자만 복구 토큰 발급. HTTP 발급 경로 없음.
- 웹: 로그인 상태 재조회, 로그인·로그아웃·현재 비밀번호를 통한 변경·분실 복구. 브라우저 저장소에 토큰을 보관하지 않으며 처리 후 입력한 비밀값을 비운다.

회원가입·메일·추가 관리자·문서/채팅/Key 기능은 추가하지 않았다. 기존 legacy 프로필 분리 유지. B05 공통 요청자/자료 접근 경계는 다음 작업이며 이 변경으로 전체 API 인증 완료를 주장하지 않는다.

## 승인값 적용과 저장 경계

S03/S04/S14 유지. 비밀번호는 Unicode code point 15~128자, 앞뒤 공백 보존, NUL 거절. B03과 같은 Argon2id 19MiB·2회·병렬1을 적용한다. 현재 비밀번호 재입력을 매 변경마다 요구하므로 비밀번호 변경은 5분 재인증 캐시보다 엄격하다. 향후 Key 변경의 재인증은 C/B05에서 연결한다.

세션은 32-byte 난수 cookie이며 DB `AdministratorSession`에는 SHA-256 digest만 저장한다. 절대 만료 8시간, 유휴 만료 30분을 서버 DB 시각으로 각각 검사한다. cookie는 HttpOnly·SameSite=Strict·Path=/·Max-Age=8시간. 승인된 공개 HTTPS origin 설정 시 Secure를 붙인다. 명시적인 loopback HTTP 시험만 Secure 예외다. 발급 후 절대 만료를 갱신하지 않는다. 로그아웃·비밀번호 변경·복구는 DB의 revokedAt으로 무효화한다. 활동 갱신은 인증된 세션 조회에서 수행한다. 만료/폐기 세션 행은 이번 단계에서 삭제하지 않으며 물리 정리·전체 보관 정책은 I 단계에서 다룬다.

`AuthenticationState` singleton에 로그인/복구 실패 횟수·창·차단 시각 및 복구 digest/발급/만료/소비 상태를 저장한다. 각 경로는 독립된 15분 창에서 실패 10회부터 1~60초 지연. 차단 중 요청은 비밀번호 hash 검증을 수행하지 않는다. 성공은 해당 시도 상태를 초기화하고, 복구 성공은 로그인 제한도 초기화한다. 관리자 이름이 달라도 같은 설치 제한을 적용한다. 로컬 복구 재발급은 복구 제한을 초기화한다.

인증 변경은 AuthenticationState 행의 FOR UPDATE로 보호한다. 세션 조회는 FOR SHARE로 같은 무효화 경계를 공유하므로 서로 다른 세션 조회끼리는 병렬 실행된다. 같은 세션의 활동 갱신은 해당 세션 행의 FOR UPDATE로 직렬화하고, 세션 행 잠금까지 얻은 뒤 clock_timestamp로 만료를 검사한다. 로그인·회전·비밀번호 변경·복구·파일 정리는 배타 잠금을 사용한다. 감사 INSERT 실패 시 비밀번호/세션/토큰 DB 변경도 롤백한다. 초기 등록은 별도 BootstrapState 잠금이고 이미 초기화된 설치의 재등록 금지는 그대로다. 비활성 관리자를 복구로 다시 활성화하지 않는다.

## 전송·파일·권한

모든 인증 요청은 `X-Townbase-Auth: 1`과 기존 등록 전송 경계를 검사한다. 변경 요청은 정확한 Host/Origin 및 JSON을 요구한다. 세션 GET은 Origin이 없는 브라우저의 같은 출처 조회도 허용하지만 custom header·Host·전송 경계는 유지한다. 공개 origin에서는 TLS 또는 정확한 trusted proxy peer의 HTTPS 전달만 허용한다. 전체 trust proxy/CORS 허용을 추가하지 않는다. 오류도 no-store·공통 보안 헤더와 안전한 정적 오류 코드를 사용한다.

복구 원문은 독립 recovery volume의 `token` 0600 파일에만 기록한다. 디렉터리는0700이며 bootstrap/문서/첨부 경로와 중첩·symlink 별칭을 거절한다. 난수32-byte·60분·1회용. DB/HTTP/발급 로그에 원문을 반환하지 않는다. 재발급 시 이전 토큰을 무효화한다. 성공 직후 및 API 기동/60초 주기에서 만료·소비 파일과 쓰기 임시 파일을 정리한다. 삭제 장애는 비밀 없는 경고와 재시도로 처리하며 API 중단 중에는 물리 삭제가 늦어진다. recovery volume은 백업에서 제외할 대상이다. 자동 백업/복원은 아직 없다.

DB와 파일을 하나의 원자적 저장으로 묶을 수는 없다. 파일 교체 뒤 commit 실패/프로세스 종료 시 파일과 digest가 다를 수 있고 인증은 거절된다. 서버 로컬 재발급으로 회복한다. 유효성·만료 검사는 파일 존재와 독립적이다. 정리는 인증 잠금을 다시 얻은 뒤 상태를 확인하므로 새 발급 파일을 잘못 삭제하지 않는다.

runtime 역할은 기존 권한에 AuthenticationState SELECT/UPDATE, AdministratorSession SELECT/INSERT 및 lastSeenAt/revokedAt 열 UPDATE, Administrator passwordHash/updatedAt 열 UPDATE만 추가한다. 관리자 이름/disabledAt·세션 expiresAt·문서·임의 DDL/DELETE는 허용하지 않는다. 준비 상태는 migration 집합뿐 아니라 두 singleton 존재도 확인한다.

## 검증

- `pnpm build`, `pnpm lint`, `pnpm db:validate`: 통과. schema 검사에는 연결하지 않는 합성 URL 사용.
- 자동 시험 총208개 통과: API/B03 DB139(일반 API124+초기 등록 DB15), B04 DB18, 배포5, 권한34, DB 단위12.
- 최종 migration 이미지에서 `TOWNBASE_SETUP_INTEGRATION=1`로 기존 초기 등록 DB 회귀까지 실행했다. B04 DB suite는 별도 DB에서 명시 opt-in 실행했다.
- 배포: 5개 통과. 실제 Vite를 통해 /auth의 Host/Origin/custom header/cookie/JSON 본문 전달까지 확인.
- B04 실 DB: 18개 통과. `TOWNBASE_AUTH_INTEGRATION=1`, postgres 호스트의 `townbase_b04_test` 전용. owner readback과 서로 다른 runtime 클라이언트 사용. 세션 digest·유휴/절대 만료 각각·회전/로그아웃·비활성/미초기화 각각·시도 제한·변경/복구·동시 소비·만료/물리 삭제·감사 실패 롤백 등을 검증한다.
- 배포 권한: postgres 호스트의 `townbase_pr34_b04_test`에서 34개 통과. 일반 배포 시험에 자동 포함하지 않는다.
- DB 없는 단위 시험: `pnpm --filter @townbase/database test --testPathIgnorePatterns=integration.spec.ts` 12개 통과.
- Docker: 별도 합성 secret/volume의 `townbase-v02-b04-test`, loopback43150. 빈 DB migration/기동 및 실제 운영 이미지의 CLI·HTTP·브라우저 확인. 비밀번호 변경/복구 후 옛 세션401·소비 토큰 재사용401·파일 물리 삭제·재등록409를 확인했고 최신 웹의 로그인·로그아웃과 변경/복구 폼 표시도 확인했다. 실제 설치 데이터/Key를 사용하지 않았다.
- 실제 조직 인증서/proxy의 운영 TLS, 네이티브 장비 성능, 전체 제품 E2E·자동 백업/복구는 이번 검증 대상과 구분한다.

재현 시 기존 DB에 시험을 실행하지 않는다. 먼저 전용 DB를 만들고 migration 이미지에 POSTGRES_DB를 해당 이름으로 지정하여 migration/seed/역할을 준비한다. owner DATABASE_URL과 runtime secret 파일을 전달한 migration 이미지에서 `pnpm --filter @townbase/api test --runTestsByPath test/auth.integration.spec.ts`를 위 opt-in과 함께 실행한다. API 런타임에는 owner secret을 주지 않는다.
