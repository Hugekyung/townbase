# v0.2 D02 — 보호된 지속 파일 관리

2026-10-29 main `29eea00`(PR #41)에서 `codex/v02-d02-file-management`로 분리했다. PRD 5.4/B05·B06, TASK V02B-D02, S05/S07/S08을 따른다. 웹은 G, DB 실행 예약/중단/재시도는 D03, 임베딩은 D04, 검색/과거 파생 참조·백업 복구 삭제 반영은 D05/I의 후속 범위다. 현재 `extracted`는 검색 가능이 아니다.

## API 계약

self_hosted의 `/files`만 활성화한다. 기존 전역 관리자 인증·Host/Origin·X-Townbase-Auth·세션·설치/workspace/소유 검사를 적용한다. 호출자는 ID로 권한을 얻지 않는다. UUID는 대소문자 모두 허용하고 정규화한다. raw storage key/서버 경로는 반환하지 않는다.

| 경로 | 내용 |
| --- | --- |
| POST /files | `{name,contentBase64}` 한 파일 등록. 새 원본과 버전1, 완료된 추출 이력을 저장하고 현재 상태를 반환(201). |
| GET /files | 원본 ID 오름차순 최대20개·nextCursor. 선택 매개변수는 cursor만 허용. 추출 본문은 목록에서 제외. |
| GET /files/:id | 현재(최고 버전) 메타데이터·추출 본문/위치·실패 코드·제품 내 참조. |
| PUT /files/:id | 같은 입력으로 교체. 원본 ID/최초 제목은 유지하고 현재 파일 이름·hash·위치를 새 버전에 기록. |
| GET /files/:id/reference | 최신 버전의 원본 복사본. 인증·소유·삭제 검사 후 파일 I/O, hash/size 검사 및 최신 신원·버전을 다시 확인. |
| DELETE /files/:id | JSON Content-Type의 `{}` 요청. 즉시 tombstone·추출문 제거, raw 정리 결과 complete/pending. 반복 삭제는 중복 성공 감사를 남기지 않음. |

모든 응답은 no-store다. 원본은 `application/octet-stream`·attachment 다운로드이며 HTML/PDF 직접 렌더를 제공하지 않는다. Content-Disposition의 파일 이름은 UTF-8 인코딩한다. 참조는 최신 버전만 가리킨다. 과거 버전 원본을 가리키는 공개 URL은 제공하지 않는다.

파일은 최대20MiB, PDF/DOCX/MD/TXT·확장자와 실제 형식 검사·D01 파서 한도를 유지한다. Base64는 표준 alphabet·padding·정규 인코딩 왕복을 검사하고 decode 전후 크기를 확인한다. 입력 본문은 정확히 두 필드만 허용한다. 비밀 파일 이름/경로는 거절하고 추출문에 기존 로컬 비밀 패턴 검사를 적용한다. 이 검사는 완전한 DLP 보장이 아니다. 검사 함수 재사용은 외부 전송/임베딩 호출을 뜻하지 않는다.

큰 JSON은 정확한 등록/교체 경로에서만28MiB로 제한한다. 본문을 읽기 전에 인증하고 파싱 후 전역 guard에서 최신 세션과 본문 범위를 다시 확인한다. 압축 본문은 거절한다. 큰 업로드 본문은 API 프로세스당1개, 미완료 본문 수신은30초로 제한한다. 다른 API는8KB를 유지한다. 현재 API는 한 요청에1파일이며 일괄20개 UI/실행 예약은 D03/G에서 연결한다.

정상 추출과 내용 오류 모두 원본/버전/완료 이력을 저장한다. scan/암호화/위장/손상/한도 오류는 failed이며 searchable=false다. failed 교체도 새 실패 버전으로 표시하고 이전 추출로 대체하지 않는다. parser_busy/unavailable·인증·저장 실패는 내용 실패로 저장하지 않는다. 응답 유실이 곧 미등록을 뜻하지 않으므로 목록·현재 버전을 다시 확인한다. D03의 영속 요청 ID/비동기 실행 예약·재시도는 아직 없다. 현재 등록 요청은 최대30초 추출을 기다리는 D02 단계이며 최종 수동 실행 계약의 완료로 표시하지 않는다.

## 저장·접근·복구 경계

`FileOriginal.deletedAt`, `FileVersion.rawDeletedAt`와 삭제 원문의 추출문-null CHECK를 후속 migration에 추가했다. 적용된 D01 migration은 바꾸지 않았다. 등록/교체/삭제 audit enum을 먼저 별도 migration으로 추가한다. 등록/교체 감사는 실제 버전 저장 transaction에, 삭제 감사는 최초 tombstone transaction에만 기록한다. 원문/파일명/비밀값을 audit에 넣지 않는다.

- `TOWNBASE_DOCUMENTS_PATH/originals`를 전용0700 경로로 사용한다. raw는 D01의0600·서버 UUID.bin 규칙이다.
- 파일 변경·재정리는 같은 DB의 advisory lock(741126,3)으로 직렬화한다. 풀 크기1의 전용 autocommit 연결을 작업 종료 때 닫아 잠금을 해제한다. 인증 transaction에 파서/파일 I/O를 넣거나 장시간 coordination transaction을 유지하지 않는다. 다른 파일 작업과 겹치면409로 거절한다.
- 인증은 추출 전과 저장 직전에 확인한다. 세션이 만료/폐기되면 등록하지 않는다. 파일을 먼저 썼지만 DB 결과가 불확실하면 원본을 무조건 지우지 않고 실제 committed version을 조회한다. DB를 조회할 수 없으면 파일을 남기고 재정리에 맡긴다.
- 시작 시와 정상 동작 중1분마다 정리한다. tombstone의 raw를 제거하고 그 성공 뒤 rawDeletedAt을 기록한다. 파일이 이미 없으면 재정리 성공으로 처리한다. unlink/DB 실패를 완료로 표시하지 않는다. 정상 저장소가 돌아오면 재시도하며,24시간 내 정리가 계속 실패하면 운영자 조치가 필요하다.
- DB에는 없는 UUID 파일은 같은 작업 잠금 아래서만 제거한다. 디렉터리는 순회 방식, 삭제 row는100개씩 조회해 전체 자료 목록을 메모리에 모으지 않는다. 알려지지 않은 파일/하위 경로/symlink는 따라가거나 지우지 않고 storage_unavailable로 중단한다. 시작 정리가 실패하면 API 시작도 실패한다.
- DELETE는 raw 정리에 실패해도 접근 차단과 추출문 제거를 유지하며 cleanup=pending을 반환한다. 현재는 chunk/vector를 생성하지 않으므로 삭제할 벡터가 없다. D04 도입 시 이 tombstone을 후보/전송 경계에 연결해야 한다. 과거 대화·Gap/draft·백업의 삭제 반영 완료를 주장하지 않는다.

runtime 역할에 UPDATE를 추가한 열은 `FileOriginal.deletedAt`, `FileVersion.extraction/rawDeletedAt`뿐이다. FileOriginal/FileVersion/FileExtractionRun의 ID·설치·소유·버전·hash 등 다른 열 수정 및 테이블 DELETE/UPDATE·TRUNCATE·REFERENCES는 허용하지 않는다.

## 실행·검증

소스 API 시험도 compiled parser/통합 시험을 소비하므로 Node24에서 먼저 `pnpm db:generate`, `pnpm build`를 실행한다. 일반 시험은 `pnpm test`, `pnpm lint`, `pnpm test:deployment`, schema 검사는 `pnpm db:validate`다.

실 DB 시험은 `TOWNBASE_FILE_MANAGEMENT_TEST=1`, 정확한 postgres/townbase_d02_test, owner DATABASE_URL·TOWNBASE_RUNTIME_PASSWORD_FILE을 요구한다. migration/runtime grants가 적용되고 Installation/FileOriginal/ModelCall이 없는 새 합성 시험 DB에서 `pnpm --filter @townbase/api test --runTestsByPath test/file-management.integration.spec.ts`를 실행한다. 이미 사용한 DB를 suite에서 자동 초기화하지 않는다. 재시험은 이번에 만든 임시 DB를 명시적으로 재생성하며 운영/기존/live DB를 사용하지 않는다. 통합 시험은 새 실제 DB·컴파일 API 전체·실제 Linux parser를 사용한다. 실패 주입은 unlink·transaction 거절·응답 유실·인증 폐기에 한정한다.

권한 suite는 기존 postgres/townbase_pr34_*_test guard로 `node --test deployment/test/runtime-role.integration.mjs`를 별도 실행한다. 일반 test:deployment에는 포함하지 않는다.

검증 로그는 `/tmp/townbase-d02-{build,lint,api,deployment,schema,image,migration,integration,acl,runtime-image}.log`에 둔다. 유료 모델 호출은 수행하지 않는다. 결과 수와 실제 운영 이미지 실행 증거는 검증 종료 후 아래에 기록한다.


### 검증 결과

- 중복 제외 자동495개: API381개(7개 opt-in DB suite/154문항은 일반 실행에서 skip), 배포24개, D02 실 DB24개, runtime 권한66개. 신규 입력/HTTP 시험29개는 API381개에 포함하며 다시 합산하지 않는다. 빌드·lint·Prisma schema·Node 문법·공백 검사도 통과했다.
- D02 DB24개는 기본4형식, 스캔/암호화/위장/손상/압축 한도 실패, 원본 ID 유지 교체/실패 교체, 같은 내용의 독립 원본, 신원/범위 거절, 삭제/반복 감사/추출문 제거/물리 삭제, unlink 실패 재정리, 중단 orphan, 알 수 없는 저장 항목 보존·시작 거절, 비밀 패턴, 다른 연결의 잠금, 페이지/cursor, rollback cleanup, 실제 commit 뒤 응답 유실, 파서 실행 중 로그아웃을 검사한다. 이미 적용된 DB를 자동 reset하지 않는 suite이며 개발 중에는 이번에 만든 임시 DB만 명시 재생성해 fixture를 맞췄다.
- 실제 Linux/amd64 production runtime 이미지를 별도로 빌드했다. 비특권 node·읽기 전용 root·cap_drop ALL·no-new-privileges·외부 게시 포트 없음에서 로그인→TXT 등록/추출→API 컨테이너 재시작→같은 세션의 독립 재조회/원본 다운로드→삭제/404·raw 디렉터리 비어 있음까지 확인했다. 운영 이미지4형식 전부를 다시 실행했다고 주장하지 않는다(4형식은 위 compiled API/실 DB suite에서 검증).
- 추가 수동 업그레이드 확인은 정확한 postgres/townbase_d02_upgrade_test 새 DB에서 D02 두 migration을 제외한 기존 migration 이력·합성 FileOriginal/FileVersion/FileExtractionRun을 먼저 생성했다. 현재 migrate runner로 업그레이드 후 기존 모든 열·JSON 추출·hash·메타데이터·시각·실행 이력을 완전 비교했고 새 deletedAt/rawDeletedAt만 null임을 확인했다. 자동495개에 합산하지 않는다.
- `/tmp/townbase-d02-runtime.log`, `/tmp/townbase-d02-upgrade.log`와 해당 `/tmp/townbase-d02-{runtime-client,runtime-seed,upgrade}.mjs`가 별도 증거다. 시험 DB·원본·secret은 이번 전용 임시 컨테이너/폴더에만 만들었다. 기존 DB/volume·실계정 비용 DB는 접근/초기화하지 않았다. 검증 후 이번 임시 컨테이너·네트워크·합성 secret/쿠키/볼륨을 정리한다.
