# v0.2 D05 — 파일 범위·삭제·교체·출처 생명주기

2026-11-01 PR #44를 main `bb5dae6`으로 동기화하고 `codex/v02-d05-file-lifecycle`에서 구현한다. PRD 5.4·5.10, TASK V02B-D05, S06·S07·S08·S09를 따른다. 기존 D04 분할 v2/고정 임베딩·명시 색인·비용 예약 계약을 유지한다.

## 제품 계약

관리자 보호 `PUT /files/:id/scope`는 JSON `{included:boolean}`만 받는다. 기존 세션·설치/소유·Host/Origin·8KB 본문 보호를 적용하고200에 별도 재조회한 파일 상태와 cleanup을 반환한다. excludedAt과 scopeRevision을 원본 단위로 저장해 제외 중 교체한 버전도 제외 상태를 상속한다. 동일 상태는 순번·감사를 늘리지 않는다. 변경은 인증 transaction의 실제 저장·file_scope_changed 감사와 함께 확정한다. 감사 실패는 범위 변경도 취소한다. 작업과 충돌하면 기존 파일 잠금 계약대로409이며 진행 중 실행을 stop한 뒤 다시 요청한다.

제외 즉시 새 검색·색인·원본 참조를 차단한다. 제외는 원본 삭제와 달라 원본/추출문은 관리자 자료 관리용으로 보존한다. 다시 포함할 때 scopeRevision을 증가시키므로 정리 실패로 옛 벡터가 남아도 재사용하지 않는다. 관리자가 별도 index를 실행해야 검색 가능해진다. 같은 내용 교체의 벡터 재사용도 scopeRevision까지 일치해야 한다. 변경/재포함만으로 유료 호출하지 않는다.

자료 관리 GET은 제외 상태·현재 추출/실패 정보 확인용이며 외부 전송 허가가 아니다. archived/draft/deprecated인 버전도 새 검색/색인과 참조에서 제외한다. 버전 상태를 편집하는 별도 제품 API를 추가하지는 않았다.

## 출처 식별과 재검사

검색 결과는 chunk ID·indexId·originalId·versionId·scopeRevision을 포함한다. 제목/URL은 권한 근거가 아니다. FileSource 식별값으로 assertFileSourcesCurrent를 호출하면 같은 인증 transaction 안에서 소유·설치·현재 버전·범위 순번·삭제·추출/색인 digest·설정/고정 모델을 검사한다. 하나라도 바뀌거나 없어지면 source_changed로 전체 사용을 거절한다. 빈 집합·20개 초과·잘못된 UUID/순번·중복 chunk ID도 거절한다.

이 함수는 C ModelExecutionService의 내부 CallBoundary.authorize에 전달하도록 구현했고 실제 합성 모델 호출에서 예약 전 재검사/차단을 시험했다. 현재 제품의 파일 임베딩 경로는 D04 guard와 파일 잠금으로 보호한다. 공개 RAG/답변 API는 아직 없으며 E에서 검색→답변 입장·결과 게시 시점과 저장 결과 재조회에 이 파일 출처 계약을 연결해야 한다. 이미 전송한 내용의 회수나 공급자 데이터 삭제를 보장하는 기능이 아니다.

fileSourceReference는 현재 접근 상태 available/deleted/replaced/excluded/unavailable를 반환한다. 저장한 범위 순번까지 전달하면 제외 후 재포함된 옛 출처도 excluded이며 링크를 반환하지 않는다. 파일 실행 목록/상세/요청 ID 조회는 저장된 원본/버전 ID와 실행 당시 sourceScopeRevision으로 현재 출처 상태를 재판정한다. 당시 순번이 불명확한 과거 이력은 unavailable로 표시하고 링크를 제공하지 않는다. 교체/삭제/제외/실패한 출처에는 resource/reference를 표시하지 않고, searchable은 현재 색인 상태를 사용한다. sourceDeleted는 삭제·없는 자료만 의미하며 단순 추출 실패를 삭제로 표시하지 않는다. 실행 당시 ID·파일명·시각·결과 이력은 보존한다.

반환하는 원본 참조는 `/files/:id/reference?versionId=<UUID>&scopeRevision=<정수>`로 고정한다. 교체 후 과거 링크가 최신 파일의 다른 내용을 내려주지 않는다. 다운로드는 I/O 전후 최신 세션·버전·범위 순번·상태를 재검사하고, 실패한 I/O에도 재검사한다. 쿼리는 두 항목 모두 또는 둘 다 없음만 허용한다. 쿼리 없는 경로는 관리자 자료 관리의 현재 원본 다운로드 호환 경로다. 실패한 최신 추출의 raw는 관리자 진단용 다운로드가 가능하나 답변용 출처로는 unavailable다.

## 물리 정리와 보관

삭제 transaction은 tombstone·추출문 제거·감사를 먼저 확정한다. 그 후 원본 파일·FileIndex/Chunk를 정리한다. DB/파일 오류면 cleanup=pending이며 삭제 완료로 가장하지 않는다. 삭제·제외·범위 순번 불일치·비active 색인은 즉시 정리 대상이다. 벡터 삭제는 Index의 실제 DELETE와 Chunk cascade로 확인한다. 비용 ModelCall·원본/버전 메타데이터·추출 이력·실행/요청 이력을 벡터와 함께 지우지 않는다.

교체 이전 버전은 즉시 검색/새 참조에서 제외하되, 동일 내용 재사용을 위해 교체 후24시간의 유예를 둔다. 새 버전 createdAt이24시간 지난 다음 정리 주기에 이전 raw·추출문·색인을 삭제한다. 최신 버전 raw는 유지한다. 현재 버전 재처리 실패/추출 digest 변경의 옛 색인도 마지막 추출 후24시간 지난 정리에서 제거한다. D04 v1처럼 설정만 오래된 현재 색인은 사용자 명시 index 전 stale로 유지한다. 삭제의 즉시 차단/24시간 이내 정리 목표와 교체 유예는 구분한다.

정리는 기존 단일 API 소유권 확보 후 시작 시·1분 주기·관련 변경 뒤 실행한다. 파일 잠금 아래100행씩 진행하고 raw unlink 성공/이미 없음 확인 뒤 rawDeletedAt과 extraction=NULL을 기록한다. 중단/실패한 정리는 다음 시작/주기에 재시도한다. API/DB가 중단되거나 저장소 장애가 지속될 때 물리 삭제 성공 시각을 보장했다고 기록하지 않는다. pending 입력은 기존 D03의 삭제 대상 검사·시작/주기 정리를 유지한다.

E의 대화·Gap 및 F 결과는 아직 파일 출처를 저장하지 않으므로 미래용 테이블이나 가짜 파생 행을 만들지 않았다. E/F는 위 식별값을 실제 저장하고 읽을 때 상태별 비노출/삭제 범위를 표시해야 한다. 기본 배포에서 비활성인 legacy Notion/Git/MCP/draft 계약은 변경하지 않는다. 백업 만료·별도 삭제 기록 보관·복구 후 재적용/공개 차단은 I의 실제 백업/복구 구현에서 완료해야 한다. 이번 DB tombstone만으로 과거 백업이나 과거 답변 전체가 삭제됐다고 표시하지 않는다.

## PR #45 리뷰 대응 (2026-11-01, 로컬 수정)

- FileRun.sourceScopeRevision을 실제 저장한다. 교체/재처리/색인은 접수 transaction에서 현재 원본의 순번을 저장하고, 최초 등록은 원본/결과를 만드는 완료 transaction에서 저장한다. 완료 시 이미 저장한 순번과 원본이 다르면 결과를 게시하지 않는다. 대기 중 순번이 달라진 작업도 외부 호출/새 결과 저장 전에 source_changed로 실패한다. 활성 대상 중복 연결도 범위 순번이 같아야 한다.
- 목록·상세·요청 UUID 조회는 공통 view에서 저장 순번을 fileSourceReference에 전달한다. 제외 후 재포함·새 색인이 끝나도 옛 실행의 순번/부모 이력을 다시 쓰지 않으며 sourceState=excluded·링크 NULL·searchable=false를 유지한다. 새 명시 retry는 새 순번을 저장한다.
- 후속 migration 20261101030000_file_run_source_scope는 nullable 양수 snapshot 열만 추가한다. 기존 행은 NULL로 남긴다. 현재 순번이나1로 추정해 채우지 않는다. 범위가 불명확하면 sourceState=unavailable·링크 NULL이며 삭제/교체/현재 제외 사실은 확인 가능한 상태로 계속 표시한다. 실제 현재 파일의 색인/검색까지 비활성화하는 처리는 아니다.
- runtime UPDATE에 완료 결과 열 sourceScopeRevision만 추가한다. 최초 등록 이외에는 이미 접수한 값을 유지하고, 완료 쓰기는 기존 running CAS와 같은 transaction에서 수행한다. 신원/대상/요청 fingerprint 등 허용 목록 밖 열과 테이블 UPDATE/REFERENCES/DDL은 계속 차단한다.
