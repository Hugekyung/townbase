# v0.2 D03 — 영속 파일 실행과 수동 재시도

2026-10-31 main `577aec3`(PR #42)에서 `codex/v02-d03-ingestion-runs`로 분리했다. PRD5.6/B07, TASK V02B-D03, 승인 S09를 구현한다. 단일 API+DB 실행 기록을 사용하고 Redis/별도 worker/예약 실행/자동 재시도는 추가하지 않는다. D04 임베딩/검색 가능 chunk·벡터와 G 웹은 후속이다.

## 요청·조회

D02의 동기 등록/교체 응답을 `202 {runId,status,existing}`로 바꾼다. POST `/files`·PUT `/files/:id`의 본문은 기존 `{name,contentBase64}`다. `X-Townbase-Request-Id` UUID v4가 필요하다. 같은 ID의 대소문자는 동일하게 처리한다. 요청자가 UUID를 보관하면 응답이 끊겨도 조회 가능하다. 잘못된 입력은 기존 형식/크기/인증 경계에서 거절하고 실행 접수로 오인시키지 않는다.

| 경로 | 계약 |
| --- | --- |
| GET /file-runs | 최근 생성 순·동률 ID 역순,20개와 nextCursor. 임의 limit 등은 거절하고 cursor도 소유/보관 범위 안의 저장 행으로 확인. |
| GET /file-runs/:id | 실행 당시 요청자/설치·설정 버전·대상/버전/hash·시각·상태·실패 이유·문서 결과·요약 카운트·retryOfId. |
| GET /file-runs/requests/:requestId | 원래 응답을 받지 못한 요청 ID로 같은 실행 조회. |
| POST /files/:id/reprocess | `{}`·새 요청 ID로 현재 버전의 로컬 추출 재처리(202). |
| POST /file-runs/:id/retry | `{}`·새 요청 ID로 failed/interrupted를 명시 재시도(202). |
| POST /file-runs/:id/stop | `{}`로 queued/running 중단(200). 이미 interrupted면 같은 결과, 완료 후 중단은409. |

모든 경로는 기존 관리자 인증/설치/workspace/소유·Host/Origin·JSON·no-store를 사용한다. 요청 ID와 workspaceId는 인증 수단이 아니다. 원문·세션/Key·임시 storage key를 실행 이력/응답에 넣지 않는다. 결과의 원본이 삭제됐으면 sourceDeleted=true·resource=null이며 과거 식별/실패 이력은 유지한다.

요청 ID는 입력 fingerprint와 DB에 연결한다. 동일 ID/동일 입력은 기존 실행, 같은 ID의 변경 입력은409다. 같은 원본/현재 버전에 대한 동일 작업이 이미 active이면 다른 요청 ID도 같은 실행으로 연결하고 별칭을 영속 저장한다. 다른 내용/다른 retry 부모가 active인 대상은 target_busy/409다. 독립 신규 파일은 내용/이름만으로 합치지 않는다. 보관 만료 후 요청 ID 보장은 종료되므로 새 작업은 새 UUID를 사용한다.

## 실행·저장·중단

- 한 설치에 running은1개. 다른 대상은 queued로 DB에 남는다. S05의 일괄20개 규모에 맞춰 queued+running은20개까지 접수하며 초과는429다. 중복 요청은 가득 차도 기존 ID를 반환한다. API는 여전히 한 HTTP 요청에1파일이며 다중 파일 화면은 G 후속이다.
- 실행은 생성 시각/ID 순서다. API 내부 dispatcher가 접수된 대기만 처리한다. 파일 잠금을 얻기 전에는 running으로 선점하지 않는다. 작업이 없는 주기 확인은 파일 잠금을 잡지 않으므로 정상 삭제를 방해하지 않는다.
- FileRun·FileRunRequest와 SQL active-target/running unique index·요청/시각/카운트 CHECK·설치별 FK로 중복/상태를 보호한다. 실행 ID와 각 결과의 원본/버전/정확한 FileExtractionRun ID를 함께 저장한다. 파일 결과와 실행 완료가 같은 인증 transaction에서 확정되므로 중간 응답 유실을 rollback으로 오인하지 않는다.
- 설정 버전은 `file-extraction-d03-v1`이다. 현재 D01의 고정 파서/한도·로컬 검사에 대한 버전이며 답변 모델/Key 설정과 혼동하지 않는다. 재시도는 새 실행/현재 설정 버전을 기록한다.
- 재처리는 기존 버전을 유지하고 새 추출 이력을 추가한다. JSON 키 순서와 무관하게 추출 내용이 같으면 unchangedCount=1, 달라졌으면 updatedCount=1이다. 내용 오류는 failedCount=1이며 이전 추출을 성공으로 대체하지 않는다. 원본이 사라져 제외된 작업은 interrupted·excludedCount=1이다. 한 실행은 한 파일이므로 부분 실패 집계용 다중 문서 배치를 선개발하지 않는다.
- stop은 DB 상태를 먼저 확정한다. 진행 파서에는 D01의 bounded SIGKILL/close 경계를 적용한다. OS 종료가 늦어도 완료 transaction은 running CAS를 통과하지 못해 늦은 파일/추출 결과를 저장하지 않는다. interrupted가 OS 종료 성공까지 보장하는 것은 아니며 D01의 미종료 자식 차단/복구 계약을 유지한다.
- 정상 종료는 queued/running을 interrupted로 기록하고 파서를 취소한다. DB가 불가하면 진단 코드만 남기고 파서 취소·소유 연결 해제를 시도한다. 강제 종료/재시작은 이전 queued/running을 api_restarted로 중단 처리한다. 자동 재실행은 하지 않는다. 운영자가 retry를 요청한다.
- 최초 실패가 파일 버전을 이미 남겼으면 retry는 같은 원본/버전을 재처리한다. 저장 전 중단됐으면 보관된 입력으로 새 실행을 수행한다. 같은 실패 등록의 진행/성공 복구가 있으면 다른 새 UUID라도 기존 실행에 연결해 원본 중복을 방지한다. 원래 실행은 retryOfId로 연결하고 source_changed/삭제/보관 만료를 거절한다. 실행 중 세션 폐기는 최신 인증 검사에서 실패하며 새 세션의 명시 재시도로만 이어간다.

## 로컬 입력·잠금·보관

`TOWNBASE_DOCUMENTS_PATH/pending`은 접수 raw 전용0700 디렉터리·0600 UUID 파일이다. originals/첨부와 분리한다. 입력을 받은 세션/토큰은 API 메모리에만 연결하며 DB에 저장하지 않는다. 재시작하면 이 연결이 없어지므로 이전 입력을 임의 권한으로 자동 처리하지 않는다. 중단/실패 입력은 수동 재시도를 위해 실행 보관 기간 동안만 유지한다. 성공/내용 실패가 실제 버전을 남기면 중복 pending raw는 정리하고 재시도는 버전 원본을 사용한다. 비밀 패턴 실패는 raw를 정리하고 동일 입력 재시도를 거절한다.

소유권(741126,4)을 전용 pool1 연결로 먼저 확보한 API만 시작 정리/실행을 맡는다. 두 번째 API는 시작을 거절한다. 소유권이 사라진 연결에서는 신규 실행을 중단한다. 파일 처리/삭제는 기존(741126,3), pending 입출력/정리는(741126,5), 짧은 DB 접수/선점/중단/완료는 transaction(741126,6)으로 분리한다. 파서/파일 I/O는 인증 transaction 밖에서 수행한다. 분산 lease·worker failover를 구현한 것으로 설명하지 않는다.

완료한 실행의 pending 입력은 작업 직후 정리하고, 시작/1분 주기로 orphan·삭제 자료·90일 지난 terminal 실행/요청 별칭을 정리한다. 원본/파생 데이터의 전체 보관은 I/D05와 구분한다. FileRun retryOfId는 부모 보관 만료 뒤에도 당시 UUID를 남기며 부모 내용/권한을 복구하지 않는다. 새 retry는 존재하는 소유 행에서만 접수한다. 삭제/다른 버전으로 바뀐 원본을 복원하는 재시도는 제공하지 않는다. DB 결과가 불확실하면 실제 행을 조회하기 전에 raw를 무조건 삭제하지 않는다.

실행 결과 상태/시각/카운트와 raw 정리는 분리한다. unlink/DB 실패를 raw 정리 성공으로 표시하지 않는다. 대기/실패 입력을 백업·복원하려면 DB와 pending/originals를 같은 복구 시점으로 취급해야 한다. 자동 백업이나 복원 후 삭제 기록 반영은 이번 완료 범위가 아니다.

## 검증 조건

Node24에서 `pnpm db:generate`, `pnpm build` 후 `pnpm test`, `pnpm lint`, `pnpm test:deployment`, `pnpm db:validate`를 사용한다. DB 없는 API 시험은 opt-in suite를 건너뛴다.

D03 suite는 `TOWNBASE_FILE_RUN_TEST=1`·정확한 postgres/townbase_d03_test·owner DATABASE_URL/runtime secret·새 합성 DB에서 `pnpm --filter @townbase/api test --runTestsByPath test/file-runs.integration.spec.ts`다. D02 회귀는 기존 guard/postgres/townbase_d02_test를 사용한다. 권한은 postgres/townbase_pr34_d03_test에서 기존 runtime-role.integration.mjs를 별도로 실행한다. suite는 기존 DB를 자동 reset하지 않는다. 개발 중 이번 전용 임시 DB만 명시 재생성한다. 기존/live DB와 유료 계정 호출을 사용하지 않는다.

증거 로그는 `/tmp/townbase-d03-{build,lint,api,deployment,schema,image,migration,integration,d02,acl,runtime-image,runtime}.log`다. 최종 결과 수·실제 이미지 재시작·업그레이드 증거는 아래에 기록했다. 사용자는 구현 요약 확인 후 커밋·푸시·main 대상 PR 생성을 승인했다.
