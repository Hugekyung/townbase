# V02B-B01 — 설치·관리자 저장 기반

작성: 2026-10-23. 기준: [TASK B01](../../TASK_v0_2_self_hosted_agent.md), [선택 기록](../../DECISIONS_v0_2_basic.md) S03·S04·S06·S07. 이번 구현은 Prisma schema와 additive migration, 실제 DB 통합 시험이다. 인증 API·로그인·파일 저장소·비밀 암호화·삭제 실행기는 이후 단계다.

## 1. 이번에 추가한 저장 관계

```text
Installation(primary, 설치 설정) ── 기존 Workspace ── 문서/질문/Gap/draft
             │
             ├── Administrator (최대 1명)
             └── InstallationAuditEvent (중요 변경 기록)
```

| 모델 | 저장 내용·제약 |
| --- | --- |
| Installation | 이름·시간대·기존 workspace 연결·초기화 완료 시각. DB CHECK가 ID를 `primary`로 제한해 설치 전체에서 최대 한 행. workspaceId UNIQUE/FK, 이름/시간대 공백 금지 |
| Administrator | 관리자 이름·Argon2id 인코딩 hash·비활성화 시각. installationId UNIQUE로 동시 생성도 최대 한 명. 평문/빈 passwordHash는 DB CHECK에서 거절 |
| InstallationAuditEvent | 설치·서버/관리자 행위자·유형이 정해진 action/outcome·서버 요청 ID·시각. 관리자 행위자는 같은 설치의 실제 관리자 FK 필요. 서버 행위자는 관리자 ID를 가질 수 없음 |

- 현재 action은 설치 생성/설정 변경·관리자 생성만 있다. 새로운 기능의 action은 그 기능을 구현할 때 migration으로 추가한다. 자유 JSON payload·본문·Key·비밀번호·프롬프트·응답을 담는 칼럼은 만들지 않았다.
- passwordHash 형식 CHECK는 해시를 생성하거나 비밀번호를 검증하지 않는다. B03/B04에서 Argon2id 비용 정책·입력 길이·검증·재해시를 구현해야 한다. 테스트 hash는 저장 검증용이며 실제 로그인 계정/비밀번호 seed가 아니다.
- `initializedAt`은 초기 등록 완료 표식이다. B03에서 토큰 소비·관리자 생성·완료 시각·감사 저장을 한 transaction으로 처리하고, 이미 완료된 설치의 재등록을 차단한다. 이번 DB 제약만으로 bootstrap 인증/토큰 재사용 방지가 구현됐다고 보지 않는다.
- B03에서 설치/관리자/감사를 한 transaction으로 저장한다. 감사 저장 실패 시 다른 생성도 rollback해야 한다. 관리자 복구는 B04에서 같은 행을 갱신하고 구세션을 무효화한다. 계정을 지웠다가 새로 생성하는 방식으로 복구하지 않는다.
- 삭제 FK는 Restrict다. 관리자/설치의 삭제가 workspace·기존 자료·감사를 연쇄 삭제하지 않는다. 감사 기록이 참조하는 관리자를 물리 삭제할 수 없으며 비활성화로 관리한다. 감사 보관 만료 정리는 I01에서 명시 수행한다. 이번에는 감사 수정 불가능/DB 관리자 변조 방지까지 보장하지 않는다.

## 2. 기존 자료 소유와 적용

- 기존 8개 모델의 행·컬럼·기본값은 변경하지 않는다. Workspace에 추가한 것은 Prisma 역방향 관계이며 기존 자료에 관리자 ID를 강제 삽입하지 않는다.
- migration 자체는 Installation/Administrator를 생성하지 않는다. 기존 workspace가 여러 개인 경우에도 이름/정렬로 하나를 추측해 가져오지 않는다. B03의 서버 운영자 초기 설정에서 사용할 workspace를 명시해야 하며, 존재하지 않으면 실패한다. 신규 설치는 기본 workspace를 준비한 뒤 같은 경로로 연결한다.
- 설치에 연결되지 않은 workspace는 새 운영 프로필에서 자료 접근을 허용하는 근거가 아니다. B05에서 인증된 관리자 → Installation → Workspace로 서버 범위를 결정한다. 요청의 workspaceId만으로 인증하지 않는다.
- 이번 단계에서는 기존 HTTP/MCP 동작·seed를 변경하지 않는다. 새 DB 관계를 만든 것과 기존 경로 보호가 적용된 것을 구분한다. B02/B05/H 완료 전에는 새 운영 제품으로 공개하지 않는다.
- 설치 이름/시간대 변경 시 workspace 소유 연결을 함께 변경하지 않는다. 서버 입력 허용 필드와 시간대 검증은 B03/G에서 구현한다. DB의 비어 있지 않음 검사가 유효한 IANA 시간대 검사를 대신하지 않는다.

## 3. 저장·비밀·파일 경계

아래 경로는 B02 이후 배포 구현 계약이며 이번에 폴더/volume을 생성하거나 파일 API를 연 것이 아니다.

| 구분 | 저장/접근 경계 | 백업·삭제 |
| --- | --- | --- |
| PostgreSQL | 내부 네트워크, 외부 DB 포트 비공개. 설치/관리자/설정/자료/이력 저장 | 암호화 백업, DB와 별도 관리하는 복호화 키. workspace 삭제로 계정/감사 자동 삭제 금지 |
| 지속 파일 | `/var/lib/townbase/documents` 전용 비공개 volume. DB 원본 ID로 조회하며 인증 API를 거쳐 접근 | 백업 포함, 삭제 즉시 새 검색/전송 차단·24시간 내 원본/벡터 정리. D/I 구현 |
| 일회성 첨부 | `/var/lib/townbase/attachments` 별도 임시 volume. 문서 경로/공용 수집과 공유하지 않음 | 백업 제외. 종료 즉시 접근 차단/삭제 시도, 생성+60분까지 만료·차단/만료+5분 내 삭제. F/I 구현 |
| master key·초기/복구 토큰 | 서버 운영자만 읽는 secret 파일. DB·정적 웹·로그·Agent 입력과 분리 | Key는 DB 백업과 다른 보호 위치에서 별도 복구 가능해야 함. 토큰 hash/만료/일회 사용과 파일 권한은 B03/B04 |
| 첨부 결과/대화 | 임시 원문과 구분한 소유자 전용 결과 저장. 공용 Question/Gap/draft 입력으로 자동 전파 금지 | 30일 보관. 원문 삭제 후에도 정책 내 결과만 조회; 실제 테이블은 E/F에서 구현 |
| 삭제 기록 | 실제 삭제 원본/버전 식별을 복원 시 적용할 별도 기록 | 백업과 함께 유실되지 않도록 별도 복구 위치 필요. I에서 구현, 삭제/만료 반영 전 복원 서비스 공개 금지 |

API Key 암호화 저장·지원 답변 모델 선택·고정 임베딩 설정은 C에서 추가한다. 지금 임의 JSON 설정 칼럼에 비밀값을 임시 저장하지 않는다. Session/토큰·작업·파일·첨부·다중 회원 테이블도 각 실제 구현 단계 전에는 추가하지 않는다.

## 4. 적용과 실패/복원 절차

1. 운영 배포는 구현/지원 검증 후 별도 승인 범위다. 적용 전 앱 버전·migration 상태를 확인하고 쓰기를 중단한다. DB/지속 파일과 별도 secret 복구 수단을 준비해 마지막 성공 백업 시각을 기록한다.
2. 새 DB는 pgvector를 제공하는 PostgreSQL에 `pnpm db:deploy` → `pnpm db:seed`. 이번 migration에 관리자/기본 비밀번호 seed는 없다. API를 사용하기 전 `pnpm db:generate`로 현재 schema client를 생성한다.
3. 기존 DB는 같은 명령으로 새 migration만 적용한다. 기존 workspace를 초기 설정에서 연결하기 전까지 초기화 완료 상태로 표시하지 않는다. 현재 단계에서 설정용 공개 API는 없다.
4. 재실행하면 이미 적용된 migration을 반복하지 않아야 한다. `db push`로 migration의 SQL CHECK를 생략한 DB를 만들지 않는다. Prisma schema만으로 custom CHECK가 모두 표현되는 것은 아니다.
5. 적용 실패 시 공개를 중단하고 Prisma migration 상태와 실제 테이블을 확인한다. 부분 생성이 남을 수 있으므로 무조건 `resolve --applied`하거나 SQL을 재실행하지 않는다. 이번 검증은 정상 적용/재실행/백업 복원을 다뤘으며 migration 중 프로세스 강제 종료까지 시험한 것은 아니다.
6. 이전 버전으로 복귀할 때는 호환성을 먼저 확인한다. 임의 down migration으로 신규 관리자/감사를 삭제하지 않는다. 불확실하면 **별도 빈 DB에 적용 전 백업을 복원**하고 동일 버전 앱·파일·키를 준비해 검증한 뒤 연결을 전환한다. 적용 후 새 자료의 손실 가능성과 백업 시각을 운영자에게 표시한다.

검증 결과와 한계는 [B01 실행 기록](v0.2-b01-verification.md)을 따른다. 이번 작은 합성 DB의 복원 성공은 I02의 전체 운영 복구·삭제 기록 재적용·4시간 목표 검증을 대신하지 않는다.
