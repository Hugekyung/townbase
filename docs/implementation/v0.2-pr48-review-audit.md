## 전체 판단

핵심 결함은 실패 뒤 상태 일관성, 백업 생성/복원 대칭, 미확인 요청 복구, 평가 재실행의 증거 보존에 집중됐다. 정상 브라우저 흐름과 통합 시험 통과만으로 이 경계를 검증한 것으로 판단한 점이 부족했다. 특히 일부 시험은 원하는 side effect가 관측되지 않아도 통과했다. 테스트 개수는 이 실패 조합의 검증을 대신하지 못했다.

P1 5개 중 평가 경로 충돌2건은 실제 실행에서 별도 volume으로 분리했으므로 기존 증거 혼합으로 단정하지 않는다. 코드의 일반 재실행 보호는 부족하다. 기존 평가를 소급 변경/새 commit으로 위장하지 말고 당시 hash·장비·한계는 그대로 보존해야 한다.

## 중복·상태 메시지

리뷰 본문의60개 요약은 인라인60개를 다시 모은 것이며 추가60건으로 세지 않는다. 별도 대화 댓글은0개다. 상태 요약인 “60 issues found” 자체는 새 이슈가 아니다. 2/4는 다른 실행기의 경로 충돌,15/49/53은 각각 unique/index/FK drift로 관련은 있지만 별도 원인이다. 11/28/44/47/59는 요청 복구 경계의 연관 결함이므로 하나의 계약으로 함께 검토해야 한다.

## 수정 우선순위

1. 삭제 실패 뒤 접근 차단, 복원 전 검증, 백업 생성/복원 한도, 기존 백업 보존·EPIPE 정리부터 처리.
2. 요청 종류별 복구·전송 전 검증·중지 대상·첨부 상태·대화 pagination을 함께 정리하고 실패/재진입 UI 검증.
3. Prisma/SQL 계약·안전한 진단·종료 신호와 약한 시험을 보완.
4. 평가 runner 재실행/manifest 계약·측정 구간·시나리오별 기록 정리. 과거 실측 증거는 변경 사실 없이 덮어쓰지 않음.

이번 점검은 코드/SQL/시험/기록을 읽은 정적 대조다. 40GiB 백업·프로세스 EPIPE·삭제 DB 실패 등 모든 지적의 실행 재현을 완료했다고 주장하지 않는다. 수정 후에는 각각 독립 실패 조건을 재현하고 readback/접근 차단/복구 ID/정리 side effect를 확인해야 한다.
