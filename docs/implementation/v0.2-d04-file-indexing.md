# v0.2 D04 — 지속 파일 분할·임베딩·검색 저장

2026-10-31 PR #43 병합 후 main `dac7e8f`를 동기화하고 `codex/v02-d04-file-indexing`에서 구현한다. 기준은 PRD5.4·TASK V02B-D04·S02/S05/S08/S09다. 첨부·Agent/답변·웹·새 Connector는 포함하지 않는다.

## 제품 계약

등록/교체·로컬 재처리의 기존 D03 계약은 유지한다. 등록했다고 즉시 외부 임베딩 호출을 하지 않는다. 관리자는 추출된 현재 원본에 `POST /files/:id/index`, 새 `X-Townbase-Request-Id` UUID v4·JSON `{}`를 보내 색인을 명시 실행한다. 기존 Host/Origin·세션·설치/소유 검사와8KB 본문 제한을 적용한다. 응답은202 `{runId,status,existing}`이며 D03 실행 목록/상세/요청 ID 조회·중단·수동 retry를 그대로 쓴다. 설치 실행1개·접수20개·재시작 중단·자동 재호출 없음도 유지한다.

파일 목록/상세는 `searchable`, `indexStatus`(not_indexed/indexed/stale), `chunkCount`를 반환한다. chunkCount는 현재 검색에 사용할 수 있는 조각 수이며 stale이면0이다. `extracted`는 파서 결과이며 색인 성공과 구분한다. Key·허용·예산·가격표가 없으면 실행 실패 이유를 남기고 벡터를 만들지 않는다. 웹의 첫 설정/색인 버튼은 G에서 연결한다.

실행별 경로·UUID·JSON `{}`·202/200 응답 및 응답 유실 복구는 [배포 안내의 파일 실행 관리](../self-hosted-deployment.md#파일-실행-관리-d03-pr-43-전달)를 따른다. 등록/교체/재처리/색인/retry의 응답 유실은 보관한 동일 UUID로 `GET /file-runs/requests/:requestId` 조회 또는 동일 요청 재전송으로 복구한다. stop은 `GET /file-runs/:id`로 상태를 확인한다.

## 분할·메타데이터·저장

- 기존 공통 FileExtraction 결과를 검증해 사용한다. PDF 페이지·DOCX 문단·MD/TXT 줄 범위·headingPath 및 원본/버전/파일 hash를 유지한다. 조각 위치는 segment 번호와 시작/끝 Unicode code point offset(0-based·끝 exclusive)도 저장한다.
- 파일 전용 분할 v2는 각 segment의 앞뒤 공백을 제거하고 연속 공백·탭·줄바꿈을 한 칸으로 명시 정규화한 뒤, 본문 순서를 유지하고 조각당 UTF-8 최대4096bytes(현재 입력 한도에서256 framing을 뺀 값이 작으면 그 값), 조각당 위치 fragment 최대128개다. 토큰 수가 아니며 기존 C의 bytes+256 상한을 추가로 적용한다. 위치 start/end는 정규화 전 원문의 Unicode code point 범위를 가리키며, 정규화된 본문과 원문 범위의 길이는 다를 수 있다. 조각 전체에 걸친 긴 공백을 flush에서 조용히 버리는 동작과 구분한다. 원본 파일·추출 JSON은 변경하지 않는다. 작은 segment는 줄바꿈으로 묶고 긴 segment는 Unicode code point 경계에서 나눈다. 인접 조각 overlap은 이번 구현에서 사용하지 않으며 J 품질 평가에서 경계 검색을 확인한다. 파일 전체를 한 번에 보내거나 한도를 넘긴 부분을 조용히 버리지 않는다.
- `FileIndex`는 버전당 한 게시 결과·원본/소유·설정 버전·고정 모델·추출 JSON의 SHA-256·조각 수를 저장한다. digest는 PostgreSQL의 `sha256(convert_to(extraction::text,'UTF8'))`로 생성/비교해 JSON key 순서 차이로 흔들리지 않는다.
- `FileIndexChunk`는 조각 원문/hash·위치/heading·sourceType=uploaded_file·knowledgeTypes/domainTags/status·sourcePriority50·requestedMode/resolvedMode를 보존한다. 색인 시 mode 값은NULL이며 E의 질문별 mode 선택에서 채운 검색 계약과 구분한다. 출처에 원본/버전/파일명/형식/hash·인증된 `/files/:id/reference`를 연결한다.
- 기존 Document/DocumentChunk는 legacy 계약으로 유지한다. 파일 전용 두 테이블은 self_hosted 신원·FileVersion 관계를 강제하며 첨부는 이 경로에 넣지 않는다. E는 내부 FileIndexService.search의 결과를 기존 mode/출처 전략에 연결한다. 질문 임베딩/공개 검색·채팅 API는 E 후속이다. 외부 vector store나 임의 플러그인을 만들지 않는다.
- 임베딩 공간은 text-embedding-3-small·1536 고정이다. [공식 임베딩 안내](https://developers.openai.com/api/docs/guides/embeddings)의 기본 차원/입력 계약을 확인했다. 기존 OpenAIProvider를 그대로 쓰고 모델/endpoint/가격표를 추가·변경하지 않는다. 길이·유한 값·float32 계산에 부적합한 극소/극대·0벡터를 서버와 vector(1536)/CHECK에서 차단한다. hash/fake fallback은 없다.

## 전송·비용·원자성

저장 원본은 인증 transaction 밖에서 한도 내로 읽고 크기/SHA-256을 버전 기록에 대조한다. 누락/변조된 원본은 전송 전에 실패하며 다음 인증/source 검사도 생략하지 않는다. 전체 추출문을 로컬 비밀 패턴 검사한 다음 분할한다. 조각 경계로 분리한 비밀을 놓치지 않게 한다. 조각별 ModelExecutionService를 통해 최신 인증·임베딩 Key·전송 허용·가격/예산·비용 예약/정산을 적용한다. 원문/파일명 자체는 기존 비용 ledger에 새로 저장하지 않는다.

C 내부 execute에 작업별 signal과 source/run admission 검사를 추가했다. 파서/파일 I/O처럼 master 파일 읽기도 인증 transaction 밖에 둔다. 준비 전과 실제 예약 transaction에서 현재 실행 running·원본/버전/소유·최신 추출을 검사한다. 예약 뒤 취소가 확인돼 전송 전이면 not_sent/0원, 전송 후 취소·불확실 실패는 unknown/예약 유지다. 실제 완료 usage가 있으면 비용은 확정할 수 있지만 중단/로그아웃 뒤 파일 결과를 게시하지 않는다.

조각 요청 ID는 실행 UUID+ordinal에서 고정 UUID v4로 파생한다. 같은 호출 ID를 자동으로 다시 유료 호출하지 않는다. 과거 호출은 비용 상태만 반환하고 벡터 결과가 없으면 결과 불가로 끝낸다. 운영자가 새 실행 UUID로 명시 retry하면 앞서 보낸 조각도 다시 과금될 수 있으며 이전 비용/unknown 예약은 유지된다. 부분 성공 조각을 숨긴 채 자동 반복하지 않는다.

네트워크 호출은 DB/인증 transaction 밖에서 순서대로 수행한다. 모든 벡터를 받은 뒤 최신 source/run을 다시 검사하고, FileIndex/모든 조각과 D03 실행 완료를 같은 transaction/CAS로 게시한다. 어느 조각·저장·취소에서 실패해도 부분 새 색인을 검색에 노출하지 않는다. ModelCall 비용 기록과 원문 결과 게시를 구분한다. 게시 전 벡터는 단일 파일 메모리에만 둔다. 현재 파일/추출/fragment 한도로 조각 수와 메모리가 제한되며 Redis/별도 worker는 추가하지 않는다.

같은 버전·추출/설정·유효 chunkBytes이면 기존 색인을 재사용한다. 같은 원본을 같은 파일 bytes/hash·형식·같은 추출로 교체했다면 유효 chunkBytes까지 같을 때 이전 벡터를 새 버전에 연결해 중복 임베딩을 피하고 metadata는 새 버전 값을 반영한다. 별도 원본은 내용이 같아도 병합하지 않는다. 비어 있거나 조각 수가 어긋난 색인은 재사용하지 않는다.

## 검색·삭제·후속 경계

파일 API와 내부 SQL 검색은 같은 조건을 사용한다: 현재 신원/설치/소유, 삭제되지 않은 원본·현재 최신 버전·rawDeletedAt 미설정 상태·active 문서·마지막 추출 성공·동일 추출 digest/설정/고정 모델. SQL에서 제외한 뒤 similarity/topK를 계산하며 다른 설치 결과를 가져온 뒤 자르는 방식이 아니다. 검색은 허용된 고정 벡터와topK1~20만 받으며 동률은 조각 ID로 정렬한다.

이 때문에 교체(실패한 최신 버전 포함)·삭제·재처리 변경/내용 실패 후 옛 색인을 새 검색에 사용하지 않는다. 과거 벡터의 물리 정리·과거 답변/Gap/draft 참조·백업 복원 후 삭제 기록은 D05/I에서 완결한다. 이번 단계가 그 전체 완료를 뜻하지 않는다. 임시 첨부/대화/Gap/새 Agent 테이블은 추가하지 않는다.

새 migration `20261101000000_file_indexes`는 FileIndex/Chunk·관계/모델/차원/벡터 CHECK를 추가하고 FileRun의 index 작업을 허용한다. 별도 기존 CHECK는 `trigger=operation`을 강제하며 `trigger=retry`만 예외다. 기존 migration은 재작성하지 않는다. runtime은 새 두 테이블 SELECT/INSERT/DELETE만 허용하며 UPDATE/REFERENCES/DDL은 거절한다. chunk의 비용 호출 FK 때문에 후속 ModelCall 보관 정리에서는 관련 색인 참조 수명도 함께 고려해야 한다. FileIndex.originRunId는 과거 출처용 UUID로,90일 실행 정리로 원본 색인이 삭제되는 FK는 만들지 않는다.

## 검증 환경과 결과

실제 유료 호출·품질 합격을 추정하지 않는다. 새 통합 suite는 `TOWNBASE_FILE_INDEX_TEST=1`과 정확한 `postgres/townbase_d04_test`의 새 합성 DB·owner URL/runtime secret을 요구한다. 전체 compiled API·실제 Linux 파서·제한 runtime 계정을 사용하고 OpenAIProvider만 합성 구현으로 대체한다. 실제 fetch는 실패하도록 막는다. 일반 API 시험은 opt-in suite를 건너뛴다.


빌드/migration 시험 환경의 Node24에서 owner DATABASE_URL을 정확한 postgres/townbase_d04_test로 준비하고 TOWNBASE_RUNTIME_PASSWORD_FILE도 지정한 뒤 db:generate/build를 선행한다. 해당 DB는 migration이 적용된 새 합성 DB여야 한다. suite는 기존 자료를 자동 reset하지 않는다.

```sh
TOWNBASE_RUNTIME_PROFILE=self_hosted TOWNBASE_FILE_INDEX_TEST=1 pnpm --filter @townbase/api test --runTestsByPath test/file-index.integration.spec.ts
```

## PR #44 리뷰 수정 (2026-11-01, 로컬 검증 완료)

- 분할 설정은 `file-index-d04-v2`. 공백 정규화를 명시하고 원문 위치를 유지한다. 기존 v1 색인은 보존하되 stale로 표시하며 명시 색인으로 갱신한다. 자동 유료 재실행은 없다.
- `FileIndex.chunkBytes`로 입장 당시 유효 분할 한도를 저장한다. 동일 버전과 동일 내용 교체의 재사용 모두 이 값을 비교한다. 입력 한도를 바꾸어도 저장 벡터 자체는 유효하므로 즉시 검색에서 숨기지 않는다. 다음 명시 색인에서 새 한도로 다시 나누며 비용이 생길 수 있다.
- `FileExtractionRun.ordinal`은 버전별 증가 순번이다. 최초1, 재처리는 공통 인증 transaction 잠금 아래 마지막 순번+1로 저장하고 UNIQUE/CHECK로 보호한다. 최신 이력은 완료 시각·무작위 UUID가 아니라 이 순번으로 읽는다. 전용 DB sequence/추가 runtime 권한은 필요 없다.
- 후속 migration `20261101010000_file_index_review`는 기존 이력의 본문·상태·시각·ID를 보존하면서 순번을 채운다. 과거의 동일 완료 시각은 실제 순서를 복원할 수 없어 실패 이력을 뒤에 두는 보수적 순서로 이관한다. 이 경우 성공 추출문이 있어도 수동 재처리 전에는 검색을 차단할 수 있다. 새 실행부터 실제 저장 순서가 보장된다. 기존 chunkBytes는 보수적으로4096이며 v1 데이터를 v2 결과로 가장하지 않는다.
- 공급자 전송 후 AbortError는 작업 signal 취소 여부에 따라 `call_cancelled`와 `provider_timeout`을 구분하며 unknown/예약은 유지한다. 이미 받은 명시적 공급자 오류는 그 이유를 보존한다.
- 비용 예약 시험은 해당 실행/조각 ID의 성공 호출과 unknown 호출을 각각 조회한다. 제목 보존은 모든 조각에서 검사한다. DB 타입 `Unsupported("vector(1536)")`은 공식 pgvector 예제와 일치해 유지한다.


이번 수정의 중복 제외 자동 검증은 **689개 통과**다: 일반 API438·배포/HTTP24·DB 단위20·D04 DB35·D03 DB34·D02 DB26·C01 DB41·권한70·업그레이드1. 일반 API는9개 opt-in suite/225개를 건너뛰었다. build·lint·db:generate·db:validate·git diff --check도 통과했다. 이전681개나 반복 실행을 더한 수치가 아니다.

D04는 기존31개에 입력 한도 변경의 동일 버전/교체2개, 완료 시각·UUID 역순의 이력 판정1개, 전송 후 AbortError 취소/예약 readback1개를 추가했다. 실제 재처리의 순번1→2 저장도 기존 시나리오에 추가했다. 공백은 긴 선행/중간/후행 공백과 Unicode 위치3개를 추가해 검증했다. 시험 도중 발견한 대용량 fixture의 topK 간섭은 자기 원본의 제품 API 삭제로 격리하고, terminal 결과와 pending 정리 잠금의 경합은 현재 로컬 pump 완료까지 기다리도록 수정했다. 운영 보호를 완화하거나 임의 유료 재시도를 넣지 않았다.
