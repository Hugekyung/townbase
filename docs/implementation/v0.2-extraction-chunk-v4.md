# R07 추출 d03-v3·색인 v4 (조각 축소·추출 보완)

2026-11-11. `codex/v02-extraction-chunk-v4`의 로컬 구현·검증 기록이다. 도입 문서의 재처리·재색인(유료 임베딩)과 답변 재측정은 이번 변경에 포함하지 않는다. 커밋·푸시·PR은 사용자 승인 전에는 하지 않는다.

## 배경

[근거 선택 보완](v0.2-evidence-selection.md)과 [예외 목록 지침](v0.2-exception-list-rule.md) 뒤에도 Q03·Q08·Q09가 남았다. 원인을 다시 보니 두 가지가 추출·분할 단계에 있었다.

1. **숫자 뒤 마침표를 문장 끝으로 처리:** 근거 단위 분리(`evidenceUnits`)는 "마침표 + 공백"을 경계로 썼다. 그래서 `’23. 3. 28`이 `’23.` / `3.` / `28 이후 …`로, `3-2. 청년 계층`이 `3-2.` / `청년 계층`으로 갈라졌다. 이 공고의 v3 조각에서 번호·날짜만 남은 줄이 38개였다. 앞서 PDF 줄바꿈으로 생각했던 `’23.\n3.\n28`의 원인이 이것이다.
2. **PDF 텍스트 조각 사이에 무조건 공백 삽입:** 파서는 pdf.js 텍스트 조각(item)마다 공백을 붙였다. 이 공고는 글자마다 따로 나뉜 구간(`랜 선 회 의 실`, `인 천 광 역 시`)과 단어 중간에서 갈라진 조각(`공고일 현|재`)이 있어 공백이 잘못 들어갔다.

또한 4KB 조각은 한 쪽의 여러 규정을 벡터 하나에 섞고, 8KB 근거 예산을 조각 3개로 채웠다.

## 원본 실측

도입 설치의 원본 PDF를 로컬에 복사해 pdf.js 조각 좌표를 측정했다. 같은 기준선에서 이어지는 조각 사이 간격(글자 높이 대비)이다.

| 조각 쌍 | 개수 | 간격 범위 |
| --- | ---: | --- |
| 한 글자씩 나뉜 한글 | 65 | −0.277 ~ −0.205 (겹침) |
| 공백 없이 이어지는 그 밖의 조각 | 190 | 대부분 −0.229 ~ +0.060. 열/표 이동 1건 −33.5 |
| 텍스트에 공백이 이미 든 조각 | 2,108 | — |

pdf.js가 실제 단어 공백은 텍스트 안에 넣어 주고 있었다. 공백 없이 맞닿은 조각은 모두 같은 단어였다. 복사본과 추출 결과는 검증 뒤 삭제했다.

## 변경

- **근거 단위(`retrieval-text.ts`):** 숫자 바로 뒤 마침표는 경계로 보지 않는다. 숫자가 아닌 글자 뒤 마침표(공백 뒤 마침표 포함)와 `!?。`은 기존처럼 경계다. 이 함수는 질문할 때 근거 구간을 고를 때도 쓰이므로, 기존 v3 조각의 구간 선택에도 같은 규칙이 적용된다.
- **PDF 조각 연결(`pdf-table.ts`의 `touching`·`itemSeparator`·`streamText`, `file-parser.ts`):** 같은 기준선(높이의 20% 이내)에서 간격이 높이의 −0.4~+0.15인 똑바른 조각은 공백 없이 잇는다. 줄 끝(`hasEOL`)은 줄바꿈, 다른 기준선·회전·먼 간격은 공백이다. 표 밖 본문과 표 칸 안 단어 모두 같은 규칙을 쓴다. 추출 한도는 `streamedCodePoints`로 최종 페이지 텍스트와 같은 구분자(직전 조각과의 `itemSeparator`)를 스트리밍 중에 세어 검사한다(아래 「PR #58 리뷰 보완」의 2차 보완).
- **조각 크기(`file-chunker.ts`, `file-index.service.ts`):** 색인 설정 `file-index-d04-v4`, 기본 목표 2,048B(`TARGET_CHUNK_BYTES`, 입력 한도-256과 비교해 작은 값)다. 상한 `CHUNK_BYTES` 4,096B와 저장 CHECK는 그대로다. overlap은 조각 한도의 1/4(512B) 이하 완전 단위로 기존 규칙과 같다.
- **설정 버전:** 추출 `file-extraction-d03-v3`, 색인 `file-index-d04-v4`. v2·v3 색인은 명시 재처리·재색인 전까지 계속 검색된다.
- **migration `20261111000000_file_index_v4`:** `FileIndex.configurationVersion` CHECK에 v4만 추가한다. 기존 행과 권한은 바꾸지 않는다.

| 조각 수 / 중앙값 크기 | 51 / 3,672B | 90 / 1,902B |
| `랜선회의실` / `랜 선 회 의 실` | 0 / 1 | 1 / 0 |
| `공고일 현 재` (단어 중간 공백) | 1 | 0 |
| 번호·날짜만 남은 근거 줄 | 38 | 0 |
| 2KB를 넘는 근거 단위(줄 중간 분할 위험) | — | 0 |
| Q01·Q02 표 행(22,302·92,800·28,302·62,800·6,000) | 3쪽 한 조각 | 3쪽 한 조각(행 전체 유지) |

새로 생긴 단어 73종(93회)을 모두 확인했다. 공백 때문에 갈라졌던 한국어 단어, 따옴표가 붙은 단어(`‘거주지’는`), 글자별로 나뉜 구간이었고 숫자·영문이 잘못 붙은 경우는 없었다. `남동구)인 자`처럼 괄호 뒤 공백이 빠진 경우가 일부 있다.

어휘 검색 순위(의미 검색은 재색인 전이라 측정하지 않음):

| 문항 | 필요한 근거 | 전 | 후 |
| --- | --- | --- | --- |

Q09는 필요한 두 사실이 2KB 조각 하나에 함께 들어가 근거 구간에 모두 담길 가능성이 커졌다. Q08은 여러 규칙과 표 행이 흩어져 있어 이번 변경만으로 해결된다고 보지 않는다. 이 표는 어휘 재현이며 실제 답변 품질이 아니다.

## PR #58 리뷰 보완

- **표 칸에서 한 조각이 나뉜 단어:** 여러 칸에 걸친 조각은 글자 폭 추정값(공백 0.3)을 실제 폭에 맞춰 줄여 단어 위치를 정한다. 폭이 좁은 조각은 추정 공백 간격이 맞닿음 기준(높이의 0.15배) 안에 들어 원문 공백이 빠질 수 있었다. 지금은 단어마다 출처 조각을 기록하고, 같은 조각에서 공백으로 나뉜 단어끼리는 항상 공백을 둔다. 맞닿음 판정은 서로 다른 조각 사이에만 쓴다.
- **공백 뒤 마침표:** 처음 정규식은 숫자뿐 아니라 공백 뒤 마침표(`제출 . 다음`)도 경계에서 뺐다. 지금은 숫자 바로 뒤 마침표만 뺀다.
- **정리(동작 불변):** 파서는 페이지 문자열을 스트리밍 중에 쌓지 않고 `streamText`로 한 번만 만든다. 상한 검사는 기존처럼 스트리밍 중 글자 수로 한다. `CONFIGURATION` 주석에 v3 설명을 더했다.
- **기본값:** `fileChunks`의 기본 조각 크기를 `TARGET_CHUNK_BYTES`(2,048)로 바꿨다. 실제 색인은 원래 값을 명시해 넘긴다. v4 migration에 `FileIndex.chunkBytes` DB 기본값 2,048을 더했고 Prisma schema도 맞췄다. `SET DEFAULT`는 기존 행을 바꾸지 않으므로 v1~v3 색인의 4,096은 그대로다.
- 새 시험: 좁은 조각의 같은 칸 단어 공백 유지, 공백 뒤 마침표 경계와 숫자 뒤 비경계, 기본 분할 크기. 세 시험 모두 수정 전 코드에서 실패함을 확인했다.
- `pnpm build`, `pnpm db:validate`, `pnpm lint`, `pnpm test`(724개 통과, opt-in DB suite 334개 건너뜀), `pnpm test:deployment`(53개), database 단위 시험(20개) 통과. 자동 DB 통합 suite는 실행하지 않았다.
- **2차 리뷰 보완:**
  - **추출 한도 계산:** 맞닿은 조각을 공백 없이 잇게 되면서, 조각마다 구분자 1자를 세던 스트리밍 한도 검사가 실제 결과보다 크게 셌다. 한 글자씩 나뉜 조각이 많으면 결과가 30만 자 안이어도 거절될 수 있었다. 지금은 `streamedCodePoints`가 `streamText`와 같은 구분자(직전 조각과의 `itemSeparator`)로 세며, 스트리밍 중 차단은 그대로다. 마지막 조각의 끝 구분자는 페이지 끝에서 잘리므로 세지 않는다. 시험은 이 합이 최종 페이지 텍스트 길이와 같고, 예전 방식보다 맞닿은 조각 수만큼 작은지 확인한다. 수정 전 코드에는 이 계산이 없다. 30만 자 PDF로 child 파서를 직접 시험하지는 않았다.
  - 칸 경계로 나뉜 조각 시험은 부분 문자열 대신 표 전체 출력(`[["Rank | Rule", "ab cd | ef"]]`)을 확인한다.
  - 수정한 migration을 새 임시 pgvector(`pgvector/pgvector:pg16`) 컨테이너에 32개 모두 다시 적용했다. `chunkBytes` 기본값 2048, `chunkBytes` CHECK(4~4,096), v1~v4 설정 CHECK를 확인하고 컨테이너를 삭제했다. 기존 행 보존은 `SET DEFAULT`의 동작에 따른 것이며 행을 넣어 시험하지는 않았다.
  - `pnpm build`, `pnpm lint`, `pnpm test`(725개 통과, opt-in DB suite 334개 건너뜀) 통과.
- 위 「실제 공고 재현」 표는 다시 측정하지 않았다. 두 동작 수정은 재현 결과의 일부 단어·단위를 바꿀 수 있다.

## 적용 방법과 남은 확인

1. 병합 뒤 API 이미지를 다시 빌드한다. migration이 함께 적용된다.
2. 문서를 **재처리**(추출 d03-v3)한다. 추출문이 바뀌면 기존 색인은 추출 digest가 달라져 검색 대상에서 빠지므로, 바로 이어서 **색인**한다.
3. 색인은 유료 임베딩 호출이다. 이 공고는 조각 약 90개다. 실행 전에 대상과 예상 비용을 확인받는다.
4. 15문항 전체를 질문마다 새 대화로 측정한다.
5. 다른 구조의 문서(OPS/SHOP 합성 문서 등)에서도 조각 연결 규칙이 정상 띄어쓰기를 붙이지 않는지 확인한다. 이번 실측은 한 PDF의 값이다.
