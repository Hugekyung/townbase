## 구현 경계

- `apps/api/src/files/`의 내부 서비스다. 공개 업로드/조회 controller나 웹 화면은 추가하지 않는다.
- PDF 페이지, DOCX 제목 경로·본문 문단 번호, Markdown 제목 경로·줄 범위, UTF-8 TXT 줄 범위를 추출한다. DOCX는 본문 문단·표 내부 문단 기준이며 머리말/꼬리말·각주·주석의 완전한 보존을 보장하지 않는다. OCR은 없다.
- 기존 Markdown 파서를 공유 export로 재사용한다. 새 업로드 문서는 `uploaded_file`로 구분하며 기존 문서/색인/mode 계약을 변경하지 않는다.
- `FileFoundation.create`는 현재 세션·설치/관리자/Workspace를 확인하고, DB transaction 밖에서 추출과 파일 쓰기를 수행한 뒤 최신 세션으로 다시 검사한다. 원본·버전·완료된 추출 실행을 하나의 transaction으로 저장한다.
- `FileFoundation.read`는 별도 인증 요청으로 소유자 범위를 다시 확인한다. 원본 ID·버전·SHA-256·본문/위치·실패 코드를 재조회하며 내부 저장 키는 결과에서 제외한다.
- 같은 내용·같은 이름도 별도 원본이다. 암묵적 병합/교체를 하지 않는다. 현재 내부 생성은 version 1이며 명시적 교체 API는 D02에서 연결한다.
- 실패한 추출은 `failed`와 허용 오류 코드로 남긴다. 성공한 추출도 `extracted`일 뿐 검색 가능한 상태가 아니다. Document/Chunk/vector/ModelCall은 생성하지 않는다.

## 고정 의존성과 처리 제한

| 항목 | 적용 |
| --- | --- |
| PDF | `pdfjs-dist` 6.4.299, Apache-2.0, 현재 Node 24.19.0에서 검증 |
| DOCX | `mammoth` 1.13.0, BSD-2-Clause |
| ZIP 사전 검사 | `yauzl` 3.4.0, MIT (`@types/yauzl` 3.4.0은 개발 전용) |
| 파일 | 지속 파일 20 MiB, 추출 30만 Unicode code points, 30초 |
| ZIP | 실제 해제 합계 100 MiB, 1,000 entries, entry 압축 비율 100배 |
| 반환 채널 | JSON 최대 8 MiB, 형식·본문 실제 글자 수·위치 구조 재검사 |
| 로컬 동시 실행 | FileExtractor 인스턴스당 1개. 후속 D02에서 단일 서비스로 사용 |

버전/라이선스/Node 지원은 공식 npm metadata와 설치된 manifest를 확인하고 lockfile로 고정했다. API의 production dependency로 배포하므로 개발용 Connector에 의존하지 않는다.
[PDF.js](https://github.com/mozilla/pdf.js), [Mammoth 보안·변환 계약](https://github.com/mwilliamson/mammoth.js#security), [yauzl](https://github.com/thejoshwolfe/yauzl).

파서는 `process.execPath`의 별도 프로세스에서 실행한다. 환경은 LANG/TZ만 전달하며 DB/Key/master 경로·NODE_OPTIONS를 상속하지 않는다. 입력은 stdin의 bytes이며 파일 경로나 URL을 받지 않는다. 결과는 전용 fd 3으로 받고 일반 stdout/stderr는 저장하지 않는다. Node permission으로 필요한 코드/의존성 읽기만 허용하며 파일 쓰기·자식 실행은 허용하지 않는다. PDF.js 텍스트 처리에 필요한 canvas native addon은 허용한다. 이것을 악성 코드용 OS sandbox나 네트워크 격리 보장으로 표현하지 않는다. [Node permission의 한계](https://nodejs.org/docs/latest-v24.x/api/permissions.html).

운영 지원은 Linux다. JIT/Wasm을 끄고 V8 old heap 128 MiB·semi space 4 MiB, Linux `RLIMIT_DATA` 512 MiB를 적용한다. 부모는 20ms 간격 RSS를 감시해 512 MiB 초과 시 SIGKILL하며 30초 timeout에도 같은 방식으로 종료하고 close까지 기다린다. DATA 제한과 RSS 감시를 전체 프로세스의 순간 RSS가 절대로 512 MiB를 넘지 않는 cgroup 보장과 혼동하지 않는다. 384 MiB DATA에서는 Linux amd64 에뮬레이션의 PDF 로딩이 실패해 승인된 512 MiB로 검증했다. 비Linux production은 거절하며 macOS 소스 시험의 자원 검증과 구분한다.

PDF.js는 bytes·로컬 CMap/표준 폰트만 사용하고 페이지별 text stream을 읽는다. Mammoth는 `externalFileAccess:false`, embedded style map 비활성으로 본문 모델을 읽고 변환 전에 문서 children을 비워 HTML/이미지를 생성하지 않는다. ZIP 모든 entry의 선언/실제 크기·암호화·중복·경로·symlink·XML DTD/entity를 먼저 검사한다. XML은 UTF-8만 허용하며 다른 인코딩은 정상 추출로 표시하지 않는다.

## 저장·DB 권한

- FileStorage는 지정된 절대·canonical 0700 root와 서버가 생성한 UUID `.bin`만 사용한다. 원래 파일명은 DB 정보로만 보존한다. 0600·배타적 생성·NOFOLLOW·fsync를 적용하고 재조회는 같은 열린 inode의 크기/종류/권한/링크 수를 검사한 뒤 크기보다 1 byte 큰 상한 버퍼까지만 읽는다.
- 현재 비공개 내부 서비스의 root는 생성자에 명시한다. 후속 D02에서 배포 `TOWNBASE_DOCUMENTS_PATH` 하위 지속 자료 경로에 연결한다. 첨부 저장소와 공유하지 않는다.
- 인증 재검사 실패/DB insertion rollback은 이번에 생성한 파일을 제거한다. 강제 종료나 DB commit 응답 유실까지 포함한 파일/DB 간 원자성·orphan 정리/재시작 복구 완료를 주장하지 않는다. 공개 업로드 전 D02/D03에서 미완료 상태·정리 경계를 연결해야 한다.
- `20261027000000_file_source_type`는 enum을 별도 migration으로 commit하고 `20261027010000_file_extraction`에서 사용한다. 파일 크기/형식/hash/저장 키·version·실패 상태·extraction 구조의 SQL CHECK, 설치/소유자/버전의 composite FK를 적용한다. db push로 대체하지 않는다.
- 제한 DB 계정에는 FileOriginal/FileVersion/FileExtractionRun의 SELECT/INSERT만 추가한다. UPDATE/DELETE 및 각 식별 열 변경은 허용하지 않는다. D02 이후 실제 수정/삭제 기능에서 필요한 열만 다시 확장한다. readiness도 세 테이블 접근을 확인한다.

- `pnpm build`, `pnpm lint`, `pnpm db:validate`, `git diff --check` 통과. DB 없는 schema 검사는 명시적 dummy URL을 사용했다.
- 정상 4형식·CRLF/제목/줄·Unicode 경계·20 MiB 허용 크기 내 과대 본문·암호화·빈 PDF·위장/손상·ZIP 폭탄/entry 수/선언 크기/경로/DTD·symlink·저장 크기·동시 파서·timeout/kill/close·비정상/과대 반환을 확인했다. timeout/반환 오류 주입 시험은 부모 제어 경계이며 악성 파일 전수 검사를 의미하지 않는다.
- 실제 DB에서 4형식 원본 bytes/hash·추출문/위치·실행 상태의 별도 재조회, 같은 내용 분리, 미인증/설치/Workspace/소유 위장 차단, 처리 중 세션 폐기, DB 실패 시 rollback/파일 정리, FK/CHECK 거절을 확인했다.
- 신규 `townbase_d01_upgrade_test`에서 D01 이전 SQL migrations→기존 DataSource/Document/metadata/1536차원 chunk→D01 SQL 적용 후 전후 JSON 전체가 동일했다. Prisma 배포 이력 검사는 별도 신규 DB의 정상 migration 시험과 구분한다.
- 실제 production 이미지의 비특권·read-only root·cap_drop ALL·no-new-privileges·network none 조건에서 PDF/DOCX/MD/TXT 추출 및 원본 재조회/삭제에 성공했다. 이 시험은 내부 서비스 실행이며 HTTP 업로드/E2E 완료가 아니다. Linux amd64 에뮬레이션이며 native 장비 성능 검증과 구분한다.
- 최초 sandbox API 실행은 loopback 권한 때문에 실패해 허용 환경에서 재검증했다. 기본 `connectors:test`의 DB 통합 2개는 로컬 DB 미연결/cleanup guard로 실패했으며 실제 DB를 사용한 Connector 회귀 완료로 표시하지 않는다. 위72개는 `--testPathIgnorePatterns=integration.spec.ts`로 명시 분리한 결과다.
- 외부 모델/실계정 유료 호출은 하지 않았다. `townbase_c01_live_test`와 사용자 `interview.md`는 변경하지 않았다.

재현은 Node 24에서 `pnpm build` 후 `pnpm test`, `pnpm lint`, `pnpm test:deployment`를 사용한다. DB 없는 패키지 시험은 `pnpm --filter @townbase/connectors test --testPathIgnorePatterns=integration.spec.ts`, `pnpm --filter @townbase/database test --testPathIgnorePatterns=integration.spec.ts`, `pnpm --filter @townbase/rag-core test`다.

D01 실제 DB suite는 `TOWNBASE_FILE_FOUNDATION_TEST=1`, owner DATABASE_URL의 정확한 `postgres/townbase_d01_test`, runtime secret 파일을 요구한다. 새 격리 DB에 실제 migrations와 runtime grants를 적용하고 API build를 먼저 실행해야 한다. 테스트가 해당 DB의 FileExtractionRun/FileVersion/FileOriginal을 정리하므로 운영 DB에 실행하지 않는다. 권한 시험은 기존 `townbase_pr34_*_test` guard를 유지한다.
