## 현재 제한

- API의 DB 쓰기는 아직 제품 기능으로 제공하지 않는다. B03 이후 각 기능에 필요한 테이블 권한은 해당 구현에서 명시적으로 추가한다. 미래 테이블 전체에 대한 자동 권한 부여는 없다.
- 파일 probe는 검사 시점의 작은 쓰기 가능 여부를 확인한다. 모든 향후 대용량 저장 성공이나 실제 디스크 전체 고장 시험을 뜻하지 않는다. 디스크 가득 참은 실패 주입 시험으로 검증한다.
- 기존 도입 환경에 자동 적용하거나 운영 DB를 변경하지 않았다. 별도 시험 프로젝트·합성 비밀·빈 volume과 전용 test DB를 사용한다.

재사용 DB의 PUBLIC 테이블/열/sequence 및 소유자의 전역·schema 기본 권한은 별도 격리 통합 시험으로 검증한다. 이 시험은 deployment/test/runtime-role.integration.mjs이며 일반 DB 없는 *.test.mjs 실행에는 포함하지 않는다. postgres 호스트의 townbase_pr34_*_test 이름만 허용하며, 실제 저장된 ACL의 보존과 명시적 정리 후 재실행을 확인한다.


### 재리뷰 검증 결과

- Linux amd64 에뮬레이션에서 **Jest63 suites/209개 + DB 없는 Node4개 + 별도 DB 권한 통합8개 = 총221개 통과**. 기존211개와 중복 합산하지 않은 최종 시험 수다. API75개·lint·전체 이미지 빌드·형식 검사도 통과했다.
- PUBLIC 테이블/열/sequence 권한3종과 소유자의 전역/public schema 기본 권한4종을 주입했다. 모두 거절되고 저장된 ACL은 그대로 보존됐다. 명시적으로 권한을 정리하면 정상 재실행됐다. 정상 DB 재실행1개를 포함해 권한 통합8개다.
- 실제 설치 DB에 PUBLIC 읽기 권한을 주입하고 API를 중단한 뒤 업그레이드했다. migration exit1·TOWNBASE_UNSAFE_RUNTIME_GRANTS·API Running=false를 관측했다. 권한 정리 후 같은 volume으로 재실행해 readyz200 확인했다.
- 별도 compose.env의43136 포트로 최초 기동·동일 설정 재실행·복구에 성공했다. API 제한 권한7종·비밀 분리·비특권/read-only 실행·재시작 파일 유지·DB 장애/복구도 다시 확인했다.
- 실제 .env 없는 임시 폴더에서는 Prisma 설정 검증이 실패하고, .env.example을 복사한 뒤에는 DATABASE_URL 해석·Prisma schema validate가 통과했다. 기존 사용자 .env는 읽거나 변경하지 않았다.
- SQL 첫 시험에서 PostgreSQL이 sequence 검사를 다른 시스템 객체에 평가하는 오류를 발견해, 객체 종류를 CASE로 보호했다. 수정 후 위 모든 정상/실패 시나리오를 다시 통과했다.
- 전용 프로젝트 townbase-pr34-round2·합성 비밀·새 volume·townbase_pr34_round2_test DB를 사용했다. 원본 로그는 /tmp/townbase-pr34-round2에 두며, 시험 후 전용 프로젝트·volume·test DB를 제거했다. 실제 운영 DB/다른 설치는 변경하지 않았다.
