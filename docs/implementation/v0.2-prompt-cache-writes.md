# 답변 호출의 프롬프트 캐시 쓰기 중단

2026-11-11. `codex/v02-prompt-cache-off`의 로컬 구현·검증 기록이다. 실제 공급자 호출로는 아직 확인하지 않았다(아래 "남은 확인"). 커밋·푸시·PR은 사용자 승인 전에는 하지 않는다.

## 관측

2026-11-11 06:45~07:59 UTC의 `rag_answer` 16건 사용량(`ModelCall.usage`)이다.

- 입력 3,084~3,951토큰 중 마지막 3토큰을 뺀 전부가 30분 캐시 쓰기(`write30`)로 과금됐다. 예: 입력 3,951, 쓰기 3,948.
- 캐시 읽기(`cached`)는 16건 모두 0이었다. 같은 모드의 질문을 30분 안에 이어서 해도 같았다.
- `gpt-6-luna` 단가는 일반 입력 100, 30분 쓰기 125, 캐시 읽기 10 nanoUSD/토큰이다(`openai-global-standard-2026-10-26`). 그래서 입력이 매번 1.25배로 과금됐다. 16건의 정산액(`chargedNanoUsd`, 건당 약 US$0.00050~0.00073)으로 다시 계산하면, 쓰기 과금 자체는 건당 총액의 약 59~82%이고, 그중 일반 입력 대비 추가분(0.25배)이 건당 총액의 약 12~16%(16건 합계 기준 약 14%)다. 이번 변경의 목표는 이 추가분을 줄이는 것이며, 실제 Luna 호출로 일반 입력 단가 과금 여부를 확인한다(아래 "남은 확인").

## 원인

[공식 프롬프트 캐시 안내](https://developers.openai.com/api/docs/guides/prompt-caching)(2026-11-11 조회) 기준이다.

- GPT-5.6 이상은 보이는 입력의 앞부분이 1,024토큰 이상이어야 캐시된다. 중단점(breakpoint)까지의 앞부분이 완전히 같아야 재사용된다.
- `implicit` 모드는 마지막 메시지 끝에 중단점을 둔다. `explicit` 모드는 개발자가 표시한 위치에만 두며, 표시가 없으면 캐시 쓰기를 만들지 않고 입력을 일반 단가로 과금한다.
- 요청은 `prompt_cache_options: { ttl: "30m" }`만 보냈다. 관측된 쓰기량은 입력 끝에 중단점이 잡힌 결과와 같다. 기본 모드는 문서에 명시되어 있지 않으므로 관측으로 판단했다.
- 답변 입력의 대부분은 질문과 근거 S1~S5라 매번 다르다. 질문과 상관없이 같은 부분은 RAG v2 지침 약 2.2KB와 응답 형식 약 1.2KB로, 합쳐 약 800토큰이다. 1,024토큰 최소에 못 미치므로 중단점을 지침 끝으로 옮겨도 캐시되지 않는다.

## 변경

- `apps/api/src/model-integration/openai-provider.ts`: 답변 요청의 `prompt_cache_options`를 `{ mode: "explicit" }`로 바꿨다. 중단점은 두지 않는다. 임베딩 요청은 원래 이 옵션을 보내지 않는다.
- 같은 요청 경로를 쓰는 근거 RAG 답변·첨부 답변·연결 확인에 모두 적용된다.
- 사용량 해석과 과금 계산(캐시 읽기·쓰기·일반 입력 구분)은 바꾸지 않았다. 공급자가 쓰기를 보고하면 지금처럼 그 단가로 정산한다.
- 비용 예약은 가장 높은 캐시 쓰기 단가 기준을 유지한다. 예약은 보수적 상한이며 정산액과 다르다.

## 검증

- 요청 본문을 고정한 시험 2개(`openai-provider.spec.ts`, `openai-provider-http.spec.ts`)를 새 옵션으로 바꿨다. 수정 전 코드에서 실패함을 확인했다.
- `pnpm lint`, `pnpm build`, `pnpm test`(710개 통과, opt-in DB suite 334개 건너뜀), `pnpm test:deployment`(53개) 통과.

## PR #56 리뷰 보완

- **쓰기 0 사용량 해석:** 공식 캐시 안내는 쓰기 내역이 올 때 두 TTL 필드를 모두 준다고만 하고, 쓰기 0일 때 `cache_write_tokens`·`cache_write_tokens_details`가 오는지는 보장하지 않는다. explicit 모드는 쓰기를 만들지 않으므로 이 필드가 빠질 수 있다. 빠진 경우를 `invalid_usage`로 거절하면 전송 후 실패라 모든 답변이 비용 미확인·예약 유지로 끝난다. 지금은 쓰기 합계가 없거나(null 포함), 합계가 0이고 내역이 없을 때만 쓰기 0으로 읽는다. 0이 아닌 쓰기에 내역이 없거나 합계·내역이 다르거나 숫자가 아니면 계속 거절한다. 실제 응답이 어느 형태인지는 아직 실제 호출로 확인하지 않았다.
- **관측 범위:** 위 관측은 `rag_answer` 16건이다. 첨부 답변과 연결 확인의 사용량은 관측하지 않았다. 연결 확인 입력은 1,024토큰 최소보다 훨씬 짧아 원래 캐시 대상이 아니다. 코드 주석도 이 범위로 좁혔다.
- **비용 비율:** 처음 기록의 "약 13~15%가 재사용 없는 쓰기"는 쓰기 할증분을 쓰기 과금 전체처럼 적은 것이었다. 위 관측 절을 정산액 기준 쓰기 과금 비중과 할증분 비중으로 나눠 고쳤다.
- 시험: 쓰기 필드 생략·0·null 4가지를 쓰기 0으로 읽고, 내역 없는 0이 아닌 쓰기 등 4가지를 `invalid_usage`로 거절하는지 확인한다. 생략 4가지는 수정 전 코드에서 실패함을 확인했다.
- `pnpm lint`, `pnpm test`(718개 통과, opt-in DB suite 334개 건너뜀) 통과. 비율은 로컬 설치 DB의 16건 `ModelCall` 읽기 전용 조회로 계산했다. 실제 공급자 호출은 하지 않았다.

## 실제 호출 확인 (2026-11-11)

PR #56 병합본(`main` `6c36c12`)으로 로컬 설치의 API를 다시 빌드한 뒤, 사용자가 채팅에서 RAG 질문 4개(Q13·Q07·Q12와 자격 제외 확인 질문)를 실행했다. `ModelCall`을 읽기 전용으로 조회한 결과다.

| 시각(UTC) | 입력 | 캐시 쓰기 | 캐시 읽기 | 출력 | 정산액(nanoUSD) |
| --- | ---: | ---: | ---: | ---: | ---: |
| 09:16:33 | 3,399 | 0 | 0 | 432 | 555,900 |
| 09:17:18 | 3,620 | 0 | 0 | 328 | 526,000 |
| 09:18:03 | 3,497 | 0 | 0 | 190 | 444,700 |
| 09:18:34 | 3,372 | 0 | 0 | 199 | 436,700 |

- Luna API가 `prompt_cache_options: { mode: "explicit" }`를 받아들였고 4건 모두 성공했다.
- 4건 모두 정산액이 입력×100 + 출력×500 nanoUSD로, 일반 입력 단가와 정확히 일치한다.
- 비교: 변경 전 같은 Q13 호출(입력 3,084, 쓰기 3,081, 출력 450)은 610,425였다. 같은 사용량을 일반 단가로 계산하면 533,400으로 약 12.6% 적다.
- 저장된 사용량은 쓰기 0으로 기록됐다. 이번 응답이 쓰기 필드를 생략했는지 0으로 보냈는지는, 공급자 원문을 저장하지 않으므로 구분하지 않았다. 두 형태 모두 쓰기 0으로 읽는다(위 "PR #56 리뷰 보완").
- 질문 4건만의 결과다. 첨부 답변과 연결 확인 호출은 이번에 실행하지 않았다.

## 남은 확인

- 첨부 답변과 연결 확인 호출의 사용량도 다음 실제 사용 때 쓰기 0인지 확인한다.
- 고정 지침이 1,024토큰을 넘게 길어지면, 지침 끝에 명시 중단점을 두고 캐시 읽기(0.1배)를 쓰는 방식을 다시 검토한다.
